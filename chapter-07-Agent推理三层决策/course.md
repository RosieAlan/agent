# 第七章：Agent 推理的三层决策机制

## 课程定位与本地对齐

- 本章依据学习者提供的第七章正文整理，范围为 7.1～7.7。
- 本章重在概念与方案选择；第八章再用 LangGraph 实现图节点、条件边和循环。
- 本地已有需求分析 `OrchestratorService`，其 `mode` 为 `fixed_workflow`。节点内部使用模型判断，节点执行路径由代码编排。
- 本地 `/api/ui-chat/chat`、`/action` 是独立的确定性 UI 状态机；页面的“待分析”表示这条 UI 流程尚未接入真实 Multi-Agent 分析。学习时保留这条边界。

## 本章目标

给定一个新任务，能先判断哪里需要运行时决策，再回答三个问题：任务走哪条链、链内下一步怎么做、结果是否需要修订。能说明 Fixed Workflow、ReAct、Plan-and-Execute、Reflexion、Critic-Refine 和 Self-Consistency 在系统中的位置。

## 7.1 固定编排与路径级推理

本地需求分析的预设结构是需求提取 → 澄清判断；若需要澄清则提前返回，否则并行执行多维度分析与风险评估，最后生成综合报告。节点内部会判断信息是否充分、风险是什么；“提前返回、并行、汇总”这些可走的路径由开发期代码列出，这叫“固定编排 + 局部推理”。

当运行时结果要改变路径，例如安全需求进入合规审查、发现矛盾后回到报告修订，就需要“路径级推理”。它可以描述为观察当前状态 → 决定下一步 → 执行动作 → 纳入新结果。

三层决策回答不同问题：

| 层级 | 关键问题 | 典型策略 | 例子 |
|---|---|---|---|
| 路由 Routing | 任务走哪条链？ | Router / Classifier | 安全需求进入安全分析链 |
| 执行 Execution | 链内如何推进？ | Fixed Workflow / ReAct / Plan-and-Execute | 查询相似需求后决定是否澄清 |
| 优化 Optimization | 结果是否需要修订？ | Reflexion / Critic-Refine / Self-Consistency | 发现报告遗漏依赖并修订 |

Fixed Workflow 仍是执行层的稳定策略。系统可以只在路由层动态选链，执行层保持固定步骤。

## 7.2 路由层

Router 依据任务特征输出目标链路标识，例如 `functional`、`performance`、`security`。下游分别使用功能、性能或安全分析 Workflow。路由适合已有多条专门链路、不同链路的工具和分析维度有明显差异的系统。单条链路可以直接执行。

判断路由是否必要：先列出任务类型与下游处理差异。若所有类型走相同步骤，保留一条 Workflow；若关键步骤不同，增加 Router 和对应链路。

设计 Router 时先定义有限的目标集合和每条链的职责，再约定路由结果至少包含目标链标识与判断依据。下游按目标链标识分发。分类置信度低时进入澄清或通用链；混合需求可采用多标签、拆分子任务或请用户确定优先分析维度。路由规则和可调用链路由系统控制。

| 输入 | 目标链 | 后续核心步骤 |
|---|---|---|
| “批量导入 Excel 数据” | 功能链 | 需求澄清、功能影响、风险、报告 |
| “一万行导入必须在 3 秒内完成” | 性能链 | 指标识别、基线、容量、报告 |
| “只有管理员可上传客户文件” | 安全链 | 权限、威胁、合规、风险 |

本地 `SelectionCard` 允许用户手动选择 `functional` 等类型，当前 `/api/ui-chat/action` 随后进入表单；它没有将任务分派给不同的真实分析 Workflow。本地 `OrchestratorService` 也只有一条预设分析链。第七章讨论的是未来把分类结果接到多条不同执行链上的目标架构。

## 7.3 执行层

- Fixed Workflow：步骤稳定、需要确定顺序和可预测结果，例如标准五段式需求分析。
- ReAct：每一步结合上一次工具结果决定下一步，适合中间观察会显著改变行动的探索任务。工程上记录决策、工具调用和观察结果即可，无需向用户展示模型私有推理文本。
- Plan-and-Execute：先生成整体计划，再执行各步骤；工具失败或前提变化时基于已完成状态重新规划。适合批量评审、步骤依赖明确的任务。

选择时先问：下一步是否必须看到上一步的具体结果才能决定？高度依赖观察时优先考虑 ReAct；任务结构可以提前展开时考虑 Plan-and-Execute；标准稳定流程使用 Fixed Workflow。

### 7.3.1 ReAct：局部决策

假设用户只说“帮我看看 Excel 导入需求是否值得做”。系统先查相似需求；查到已有单条导入能力后，再决定检查复用与冲突；发现最大行数缺失后，向用户澄清。每轮可归纳为当前状态 → 选择允许的动作 → 执行工具 → 读取结果。下一步由最新观察决定。工程实现需要控制可用工具、最大轮次与停止条件；可观测性聚焦动作、工具结果和状态变化。

### 7.3.2 Plan-and-Execute：全局规划

评审 50 条需求时，先规划“查询需求 → 查冲突 → 过滤阻断项 → 估算剩余项 → 汇总报告”的依赖，再逐步或并行执行。若查询失败或中间结果使原计划失效，基于已完成步骤、失败项和剩余目标进行 Replan。Executor 可以调用确定性 Workflow；某个模糊子任务也可以使用受控的 ReAct 循环。

### 7.3.3 如何选择

| 策略 | 下一步何时决定 | 适合情况 | 关键控制 |
|---|---|---|---|
| Fixed Workflow | 开发期安排主要路径 | 单条标准需求、步骤稳定 | 条件分支和异常处理 |
| ReAct | 每次观察后决定 | 工具结果会显著改变后续行动 | 工具白名单、轮次和停止条件 |
| Plan-and-Execute | 开始时规划整体，必要时重规划 | 多条需求、依赖清晰、可批量执行 | 已完成状态、失败恢复和 Replan |

步骤数量是参考线索；核心判断依据是“后续路径对未知中间结果的依赖程度”。

## 7.4 优化层

- Reflexion：评估整条执行结果，形成改进意见后重新执行；适合执行过程本身可能出错的长任务。
- Critic-Refine：指出最终结果的具体问题并局部修订；适合报告遗漏、结构和表达问题。
- Self-Consistency：对明确答案的分类或评级多次独立判断，再聚合结果；适合离散判断题。

质量校验先定义可检查标准；重跑、局部修订和多次判断都有额外延迟与成本，应按问题范围选用。

### 7.4.1 Reflexion：整链回看

若提取阶段漏掉“最多一万行”，后续分析与风险评估都建立在不完整输入上。Evaluator 对照原始需求检查最终报告，指出漏提约束；Reflector 形成改进意见，Actor 从受影响的上游步骤重新执行。需要限定重试轮次并保留每轮评价，避免无限循环。

### 7.4.2 Critic-Refine：局部修订

若上游提取和评估完整，报告的“排期建议”段落遗漏了现成的外部系统依赖，Critic 可以指出具体缺口，Refiner 只修订该段。修订应引用已有事实和中间结果，避免引入未经证实的新约束。

### 7.4.3 Self-Consistency：独立判断后聚合

风险等级等离散判断可独立运行多次，再比较结果或投票。各次判断需尽量独立，并保留分歧以供复核。多数结果是稳定性线索，仍需对照业务证据；长报告和开放式创作缺少直接可投票的答案。

| 问题范围 | 推荐策略 | 主要成本 |
|---|---|---|
| 上游理解错误，后续连锁受影响 | Reflexion | 重新执行部分或整条链 |
| 中间结果可信，最终文案局部缺漏 | Critic-Refine | 评审与局部生成 |
| 明确标签或等级的判断不稳定 | Self-Consistency | 多次独立模型调用 |

执行前先定义验收标准，例如“报告必须覆盖原始约束、引用来源可追溯、结论前后一致”。优化层负责对照标准检查并修正结果；高影响决策还应使用确定性规则或人工复核。

## 7.5 按层组合

单条功能需求：任务类型 Router → 对应 Fixed Workflow → Critic-Refine 修订报告。批量需求评审：Planner 生成计划 → Executor 批量执行，部分步骤可以调用 ReAct 或 Fixed Workflow → Critic 检查最终汇总。同一执行层也可以组合策略，前提是明确每层的输入、输出和终止条件。

### 7.5.1 按任务选组合

| 任务 | 路由层 | 执行层 | 优化层 |
|---|---|---|---|
| 单条标准需求 | 多条专门链存在时分类 | 对应 Fixed Workflow | 报告有局部缺漏时 Critic-Refine |
| 模糊需求探索 | 单链时直接进入执行 | 受控 ReAct，依观察选择工具 | 上游理解错误时 Reflexion |
| 50 条需求批量评审 | 选择批量评审链或拆分任务类型 | Plan-and-Execute；步骤内可复用 Workflow / ReAct | Critic-Refine 检查汇总报告 |
| 风险等级判断 | 选择对应判断服务 | 简短固定流程 | 有分歧时 Self-Consistency + 业务规则复核 |

三层可独立取舍：只有一条执行链时可直接进入执行层；结果已有可靠规则校验且质量达标时直接交付。组合时定义三种交接数据：路由输出目标链标识，执行输出结果与证据，优化输出质量结论和修订结果。

### 7.5.2 需求分析系统的目标演进

产品经理输入“批量导入 Excel，只允许管理员上传”，系统先识别功能与安全两个维度；执行层将它们交给对应分析步骤并合并证据；Critic 检查报告是否覆盖权限约束，必要时局部修订；最后把可信结果组织成第六章 UI 协议。这里描述的是目标架构。本地 `/api/ui-chat/chat` 仍是独立的演示状态机，当前没有调用多条分析 Workflow。

增加新层时先写清触发条件与成本上限：Router 何时澄清或多标签处理、ReAct 最多循环多少轮、Replan 如何保留完成状态、优化最多修订多少次。

## 7.6 LangGraph 承载方式

Router 对应节点和条件边；Fixed Workflow 对应固定节点链或子图；ReAct 对应 Agent 与工具之间的循环；Plan-and-Execute 对应 Planner、Executor 和 Replan 边；Critic-Refine 对应评审与修订节点。共享 State 保存分类结果、中间产物、已完成步骤和修订轮次。第八章再实现这些结构。

## 7.7 本章验收

给定“单条标准需求”“模糊需求探索”“50 条批量需求评审”“报告遗漏依赖说明”四个任务，能分别指出需要哪一层决策、推荐哪种策略、理由是什么。能够解释本地五段式编排与 UI 状态机的实际边界，并画出 Router → Workflow → Critic → UI 的目标结构。
