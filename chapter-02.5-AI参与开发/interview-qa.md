# 第 2.5 章面试题 & 答案

### Q1：Superpowers 主要解决 AI 编程的什么问题？
AI 太容易过早进入实现：需求还没说完就开始建文件，还自作主张扩展功能。Superpowers 把"先写再说"改成按工程阶段推进：澄清需求 → 定方案 → 拆计划 → 带测试执行 → review → 收尾，每个阶段只做该做的事。它解决的是"开发过程是否可控"。

### Q2：ui-ux-pro-max 是什么？和 HeroUI 这类组件库有什么区别？
它是给 AI 补设计经验的知识层：做 UI 任务时自动检索适合的风格、配色、字体、布局建议交给模型参考。它是"设计顾问"，不是"页面生成器"。组件库提供现成的按钮、表格等代码；ui-ux-pro-max 不提供组件，而是提供"怎么搭配才专业"的判断。它解决的是"前端结果是否足够成熟"。

### Q3：为什么先用 Superpowers 做完后端骨架，再用 ui-ux-pro-max 做前端？
前端依赖后端：要做哪些页面、调哪些接口、拿到什么数据，要等后端定下来才明确。需求和接口还在变时就打磨界面，等于给不稳定的需求套皮，后面接口一改页面就要返工。页面目标明确后，设计增强才有价值。

### Q4：Superpowers 工作流分哪几个阶段？
1. 需求澄清（brainstorming）：把模糊需求变成确定的设计决定
2. 准备与计划（using-git-worktrees、writing-plans）：隔离工作区，拆成小步可验收的计划
3. 执行（executing-plans / subagent-driven-development + TDD + code review）：按计划逐步做，测试和审查持续约束
4. 收尾（finishing-a-development-branch）：确认测试、回归、分支如何处置

### Q5：git worktree 在这个流程里起什么作用？
同一个仓库再开一个工作目录切到新分支，AI 在里面改代码，原目录不受影响，改砸了删掉即可。前提是项目是 git 仓库。

### Q6：为什么计划每一步要拆得很小？
长任务会导致上下文膨胀，对话变长后早期细节会被压缩或遗忘。步骤小，每步要记住的东西少，不易跑偏；计划写成文件，对话中断或压缩后也能从文件恢复进度。另外一步里包含的决定越多，AI 执行时自行拍板的地方越多，越容易发散。

### Q7：为什么说很多问题出在收尾而不是生成？收尾容易漏什么？
代码生成出来不等于完成。常漏的有：没确认测试是否通过、没做回归（改 A 是否弄坏 B）、没说明分支怎么处理（合并/PR/保留/删除）。没验证就说"完成"是最常见的问题。

### Q8：TDD 是什么？为什么写完测试"必须先看到它失败"？
先写测试再写代码，循环为红（测试失败）→ 绿（写最少代码让它通过）→ 重构。必须先看到失败，是为了证明这个测试真的能抓住"功能没实现"的情况。一个从没失败过的测试可能根本没在测东西（比如忘了 await、断言永远成立），先写代码后补测试时这种假绿很难发现。

### Q9：为什么 AI 编程特别适合 TDD？代价是什么？
一是"做完了"有客观标准，不看 AI 自己怎么说；二是防止"测试迁就代码"——先写代码再让 AI 补测试，它会照着有 bug 的实现写测试，结果全绿但 bug 还在。代价是节奏变慢，所以小改动、样式调整、探索性原型不一定要走 TDD。

### Q10：TDD 和 e2e 是什么关系？
不是同一类东西。TDD 是开发方法（什么时候写测试），e2e 是测试类型（测多大范围）。测试金字塔：底层单元测试多且快，中间集成测试，顶层 e2e 少、慢、覆盖完整用户流程。常见做法是开发时对单元/集成测试用 TDD，核心用户路径用少量 e2e 放进 CI。Nest 里的 e2e 是发 HTTP 请求测接口；浏览器级 e2e 要用 Playwright、Cypress。

### Q11：RBAC 是什么？为什么权限要挂在角色上而不是直接给用户？
基于角色的权限控制：用户属于角色，角色拥有权限。直接给用户分配时，给 100 个运营加一个权限要改 100 次；挂在角色上只改一次角色即可，便于统一管理。

### Q12：为什么做权限系统第一步是让 AI 先问问题而不是写代码？
权限系统最容易出问题的是边界不清时 AI 默认做太多假设：你要的是按钮级后台权限，它可能做成带租户、审计的企业权限平台。多做的部分单独看不一定错，但会大幅拉高复杂度且不是当下所需。先问清粒度、超管绕过、refreshToken 是否落库、审计日志、组织租户维度，才能定下设计。

### Q13：accessToken 和 refreshToken 的区别？refreshToken 落库有什么好处？
accessToken 用来访问接口，有效期短；refreshToken 用来换新的 accessToken，有效期长。refreshToken 存数据库后，服务端可以主动让它失效（用户被禁用、改密码后强制重新登录）；不落库则签发出去收不回，只能等自然过期。

### Q14：Spec 里为什么要写"这次明确不做什么"？
AI 倾向于把功能做全做大。不写明边界，执行时会不断顺手扩展。而且核心决定（模块怎么拆、权限怎么命名、前端怎么判断权限）不先写死，计划拆得再细也只是把摇摆的决定拆得更碎，前后步骤可能出现不一致，比如权限一会叫 `user:delete` 一会叫 `DELETE_USER`。

### Q15：计划为什么不能写"实现用户模块"？进入下一阶段前要确认什么？
"实现用户模块"里藏着字段、密码加密、真删假删、分页等一堆决定，AI 会边做边自己拍板。计划要拆到每步有明确交付物和验收标准。计划是执行顺序，不是目录结构。进入下一阶段前确认两件事：当前阶段验收通过；已 git commit 作为存档点，下一阶段改砸可以回退。

### Q16：Nest 里 Guard 和 @Permissions 装饰器怎么配合做鉴权？
请求先过 JwtAuthGuard 校验 Token（无效返回 401），再过 PermissionsGuard 比对权限（不足返回 403），通过才执行接口。@Permissions('user:delete') 给接口贴上所需权限的标签，PermissionsGuard 读取标签判断，权限规则直接写在接口旁边，清晰集中。

### Q17：401 和 403 的区别？为什么没权限必须返回 403？
401 是"不知道你是谁"（没带 Token、过期、伪造）；403 是"知道你是谁但你没权限"。前端处理不同：401 让用户重新登录，403 提示没权限。如果没权限也返回 401，用户点删除会被踢回登录页，重新登录后再点又被踢，形成死循环。

### Q18：前端已经隐藏了没权限的按钮，为什么后端还必须鉴权？
前端隐藏只是体验，不是安全。任何人都能通过开发者工具或 curl 直接调接口，绕过前端。真正拦住请求的只能是后端。这也是验收时要用 curl 专门测"无权限删除返回 403"的原因。

### Q19：给 ui-ux-pro-max 的设计要求为什么要写到色号、像素这么具体？
"好看一点"这种要求每次理解都不同，结果不可控也没法验收。具体到色号、宽度、弹窗形式、指定组件库并禁止自造轮子，才能得到一致、可检查的产出。本质仍是约束边界。

### Q20：集成阶段要做哪些事？为什么需要种子数据？
联调（配置 API 地址、封装请求自动带 Token、统一处理 401 自动刷新/跳登录和 403 提示）、整理本地启动和端口、编写初始化脚本、输出 README。新数据库是空的，没有管理员就登录不了，没有权限数据就无法分配，所以需要种子脚本首次写入超管、角色、菜单和权限。

### Q21：Superpowers 全流程什么时候适合，什么时候不适合？
适合中大型、多模块联动、需要跨会话推进、需要可复盘的开发。不适合小 bug、一次性脚本、快速验证原型、方向还在变的创意型工作。一句话：小任务轻流程，大任务重流程。

### Q22：这套流程有哪些现实限制？
Spec/Plan 有前置成本，小任务不划算；TDD 让 AI 变慢；ui-ux-pro-max 效果受代码基线限制，项目本身混乱它也救不了；人工决策不可替代——引入哪些复杂度、哪些边界这次不做、求快还是求稳，要人来定。

### Q23：用 AI 跑完整开发流程时，成本上要关注什么？
不同阶段用不同强度的模型（规划用强模型，简单执行可用便宜模型）；缓存命中率和 Prompt 前缀是否稳定；每一步的输入、输出、缓存 Token 各多少；优化上下文后成本实际下降多少。Agent 工程不只是能不能生成，还要能长期、稳定、可控地运行。
