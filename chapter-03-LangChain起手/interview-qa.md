# 第三章面试题 & 答案

## 一、为什么用 LangChain

### Q1：已经有 OpenAI SDK 了，为什么还要引入 LangChain？
只调一次模型 SDK 就够了，但进入业务系统后问题会变成"能不能长期维护"：提示词越来越多、散落各处；模型结果要给程序用，格式必须稳定；模型需要调工具、查资料；多个步骤要固定成可复用、可测试的流程。LangChain 把提示模板、模型、输出解析、工具调用、链式编排放进同一套编程模型，提前把这些工程问题收口。它不是"换一种写法调模型"。

### Q2：为什么写代码前要先把任务定义成固定结构？
如果只说"提取核心目标和关键词"，边界、粒度、是否唯一正确都说不清，更关键的是写测试时不知道断言什么，也就无法判断改动后变好还是变差。所以先把任务钉死成 `{ action: string, constraints: string[], entities: string[] }`，每加一层能力都能对照同一个目标验证。这和第一章"先定义返回结构，再写调用逻辑"是同一原则。

### Q3：LangChain 的哪些能力对应第一章手写的封装？
- system / user 分工 → `SystemMessage` / `HumanMessage`
- Prompt 集中管理 → `prompts/` + `ChatPromptTemplate`
- 统一调用层 `LLMClient` → 模型工厂 `createChatModel()`
- 先定义返回结构 → zod schema
- `generateJSON` + 校验函数 → `withStructuredOutput()`
- 封装成可复用模块 → `pipe()` 链 + 业务 Service

### Q4：模型能力为什么放在 Nest 后端，而不是 Next？
API Key 不能暴露到浏览器；工具、检索、日志、限流、重试、监控需要统一治理；AI 请求常常耗时长、要流式输出、要串工具和检索，Nest 的模块化、依赖注入、守卫更适合；后端需要独立扩容和告警。Next 适合做前端应用层和一层薄 BFF，Nest 做长期承载 AI 能力的后端底座。

## 二、配置与模型

### Q5：API Key、模型参数、提示词分别放哪里？为什么分开？
- API Key、服务地址 → 环境变量（`.env` / 部署时注入）：敏感且每个环境不同，不能进仓库
- 模型名、温度、功能开关 → YAML：不敏感但经常调，可以提交给团队看
- 提示模板 → 代码 `prompts/` 目录：需要版本管理和类型检查

分开后，调参数不会碰到密钥，换密钥不用改代码。

### Q6：`load(raw) as Config` 能保证配置内容正确吗？
不能。`as` 只是让 TypeScript 相信类型，编译后就消失，运行时不做检查。YAML 写错类型照样读取成功，要到使用时才报错。要真正保证需要运行时校验，比如用 zod 校验配置。

### Q7：为什么要用统一的模型工厂，而不是各处 `new ChatOpenAI()`？
换模型、改参数只需改一处；避免有人漏配温度等参数导致同一功能表现不一致；以后统一加日志、重试也只改工厂。对应第一章的统一调用层。

### Q8：为什么只要"兼容 OpenAI 格式"的服务都能用？
OpenAI 接口格式已是事实标准，很多厂商提供同格式接口。代码按这个格式写，通过 `configuration.baseURL` 指定服务地址，换厂商只换地址和 Key，代码不改。

### Q9：invoke、stream、batch 有什么区别，各适合什么场景？
- invoke：一次拿完整结果，默认选择，适合接口返回 JSON、链路早期搭建，便于重试超时缓存
- stream：边生成边返回，强调体验，适合聊天逐字显示、长文生成
- batch：多条输入一起处理，强调吞吐，适合历史数据回填、改 Prompt 后批量回归评测

一句话：stream 是"一条慢慢出"，batch 是"多条一起出"。

### Q10：为什么需要稳定 JSON 时一般不用 stream？
流式返回的是一段段碎片，传完之前不是完整合法的 JSON，无法解析也无法断言。通常先用 invoke 拿结构化结果，再决定解释性文字是否流式展示。

## 三、提示模板与链

### Q11：什么时候该把 Prompt 抽成模板？
同一段提示词出现在两个以上地方，或者改一次提示要动多个文件时。抽出后改措辞只动 `prompts/` 里的文件，业务代码不动。

### Q12：模板里想写 JSON 示例 `{"action": "..."}` 要注意什么？
花括号在模板里表示变量，直接写会被当成变量而报错，要写成双花括号 `{{"action": "..."}}` 转义。

### Q13：为什么要有一个只渲染模板、不调模型的预览接口？
不花钱、速度快，模型回答不对时先确认"到底发给模型的是什么"：变量有没有替换、Prompt 本身有没有问题。先确认输入对，再怀疑输出。

### Q14：为什么模板、模型、解析器能用 `pipe()` 接在一起？
它们都是 Runnable，统一拥有 invoke / stream / batch。`pipe()` 把上一个的输出接到下一个的输入：`{input}` →（模板）消息数组 →（模型）AIMessage →（解析器）字符串。每节的输出类型正好是下一节需要的输入类型。

### Q15：StringOutputParser 起什么作用？为什么要单独作为一节？
把模型返回的 AIMessage 对象转成纯文字。单独作为一节，是为了之后能只替换这一节（比如换成结构化解析），前面的模板和模型不用动。

### Q16：什么时候该把调用收成链？
连续两次以上写出"同一个模板 + 同一个模型 + 同一个解析"的组合时。从这时起要维护的不是某次调用，而是一条业务流程。先把流程写成链，再按需要选 invoke 还是 stream，流程和返回方式分开。

## 四、结构化输出

### Q17：`withStructuredOutput` 在背后做了什么？
1. 把 zod schema 转成 JSON Schema 随请求发给模型，要求严格按结构返回
2. 把返回的 JSON 文本解析成对象
3. 用 zod 校验结构，不符合就报错

对应第一章手写的"Prompt 里描述格式 + JSON.parse + 校验函数"，返回值直接是对象。

### Q18：结构通过了 zod 校验，内容就一定对吗？
不一定。schema 只保证"形状"：字段有没有、类型对不对。实测中不加规则 Prompt 时，模型返回了英文、数组里塞 JSON 字符串，却完全通过校验。内容质量要靠 Prompt 规则约束，再靠测试和评估发现问题。两者缺一不可。

### Q19：zod 和 TypeScript 类型有什么区别？`z.infer` 有什么用？
TypeScript 类型只在编译时存在；zod schema 运行时也在，可以校验真实数据。`z.infer` 从 schema 自动推导出 TS 类型，只写一份定义，运行时校验和编译时类型都有，永远不会对不上。

### Q20：`.describe()` 有什么用？
给字段加说明，这段说明会随 JSON Schema 发给模型，告诉它每个字段该填什么。描述写得好不好，直接影响模型填得准不准。

### Q21：结果结构为什么放共享包？
后端用它约束模型输出，前端用推导出的类型展示结果。放共享包，改一个字段前后端同时生效，不会各写一份越改越不一致。

### Q22：结构化输出有几种实现方式？遇到过什么兼容问题？
常见有 jsonSchema（通过 `response_format` 要求按 JSON Schema 返回）和 functionCalling（通过强制工具调用拿结构化参数）。实践中用通义千问思考模式时，默认的 jsonSchema 可用，指定 functionCalling 会报 400，因为思考模式不支持强制 `tool_choice`。不同模型厂商支持的方式不同，要实测确认。

## 五、工具调用

### Q23：为什么需要工具调用？
模型的判断是概率性的，但有些答案是确定的或只能从外部获取：规则校验（正则）、业务定义（字典/数据库）、订单状态（查库）。工具把这些交给代码执行，模型只负责判断什么时候查、查什么。一句话：模型负责决策，工具负责给出确定性结果。

### Q24：一个工具由哪几部分组成？模型能看到什么？
函数（真正执行的逻辑）+ name + description + schema。模型看不到函数代码，只能看到名字、说明和参数结构。模型判断要不要调工具全靠 description，写得模糊模型就不知道何时用。

### Q25：模型返回了 `tool_calls`，工具执行了吗？
没有。`tool_calls` 只是模型的调用申请（工具名、参数、调用 id），真正执行是应用代码的事。

### Q26：完整的工具调用闭环是怎样的？为什么要调用两次模型？
1. 模型根据问题返回 `tool_calls` 申请
2. 代码按名字找到工具并执行，把结果包装成 `ToolMessage` 追加到消息列表
3. 带着工具结果再调一次模型，生成最终回答

第一次决定调什么，第二次根据工具结果回答。第一次的回复也要追加进消息列表，否则模型不知道自己申请过什么。

### Q27：`ToolMessage` 里的 `tool_call_id` 有什么用？
标明这个结果对应哪一次调用申请。模型一次可能申请多个调用，靠 id 把结果和申请一一对上。

### Q28：工具闭环代码里 `if (!targetTool) continue` 防什么？
防模型编造不存在的工具名。模型输出不能全信，执行前要在代码里校验。

### Q29：为什么要"模型申请、代码执行"，而不是让模型直接执行？
可审计：调用什么、参数是什么全有记录；可限权：执行前检查当前用户有没有权限；可定位：失败时能分清是模型申请错了还是工具执行出错。高风险操作尤其需要。

### Q30：什么时候该用工具，什么时候用 Prompt / 结构化输出就够了？
答案依赖外部事实、外部规则或真实动作时用工具；否则优先 Prompt 和结构化输出。典型场景：规则校验、事实查询、流程编排、高风险操作闭环。

## 六、收束与测试

### Q31：业务入口为什么单独放，而不是继续用 `/api/langchain/...`？
`/api/langchain/*` 是按技术分类的演示接口；`/requirement/extract` 是按业务命名的入口。调用方只需知道"抽取需求调这个"，不关心背后是链、结构化输出还是工具。接口名描述业务能力，不描述实现技术，后端换实现调用方无感。

### Q32：前端在这条链路里的职责边界是什么？
只做三件事：采集输入、调用统一接口、展示结果。不知道用了哪个模型和链，不解析、不校验、不写 Prompt。前端越薄，后端迭代时需要联动改的地方越少。

### Q33：Nest 里一个模块的 Service 要给另一个模块用，需要做什么？
提供方模块在 `exports` 里导出，使用方模块在 `imports` 里引入提供方模块，两步缺一不可。

### Q34：单元测试里为什么要把依赖换成 mock？
被测对象只需要依赖"存在"，并不真正用到。真实的 RequirementService 会读配置、创建模型、调接口，导致测试变慢、花钱、依赖网络。用 `useValue: { extract: vi.fn() }` 提供假对象，测试只关注被测逻辑。不提供则 Nest 无法解析依赖直接报错。

### Q35：单元测试和 e2e 测试有什么区别？
单元测试只装被测 Controller 加 mock 依赖，直接调方法；e2e 装整个应用模块，真的发 HTTP 请求，验证路由、模块注册和应用能否启动。Nest 的 e2e 用 supertest 在内存中发请求，不开浏览器。

### Q36：调用真实模型的测试怎么写断言？为什么默认跳过？
不锁死具体措辞（同一句话模型可能给出不同的 action），只断言结构约定（字段类型、数组非空）和关键语义命中（结果包含"手机号"）。默认跳过是因为它花钱、依赖网络、耗时长，平时和 CI 里不该每次都跑，通过环境变量开关按需打开。

## 七、实战踩坑（体现真实经验）

### Q37：ESM 项目里 import 有哪些容易踩的坑？
相对路径必须写 `.js` 后缀；没有 `exports` 字段的包，子路径也要写 `.js`（如 `supertest/types.js`）；装饰器参数用到的纯类型要 `import type`。脚手架模板也可能只改了一半，不能默认它是对的。

### Q38：为什么 `.env` 要在 `main.ts` 的第一个 import 里加载？
ESM 会先执行完所有 import，再执行文件里的其他代码。写在模块最外层的 `createChatModel()` 在被导入时就执行，如果 `.env` 在 import 之后才读，创建模型时 API Key 为空，调用时报 Missing credentials。写在类属性里的则在实例化时执行，不受影响。把加载放进单独文件并作为第一个 import 可以一劳永逸。

### Q39：接口返回 500，怎么排查？
500 的具体原因只在服务端日志里。看不到日志时，可以用另一个端口单独启动一份服务复现同样的请求，从日志里拿到真实报错，再沿调用栈从上往下找出错点和调用方。

### Q40：服务启动报 `SyntaxError: Unexpected token 'with'`，可能是什么原因？
Node 版本太老，不认识 import attributes 语法（`import x from './a.json' with {type: 'json'}`）。实际案例是 nvm 全局切到了 Node 14。堆栈路径没有 `node:` 前缀也是老版本 Node 的特征。先检查 `node -v`。
