# 第一章：把模型变成能力

如果说序章讨论的是开发范式为何会改变，那么从这一章开始，正式进入实践层面：一款智能体究竟应该如何着手开发。

当我们谈"开发智能体"时，究竟是在开发什么？是一个会聊天的模型、一个能执行任务的流程，还是一种能够接入系统并持续运行的工程化能力？

本章先不讨论复杂 Agent 设计，而是回到最基础的一层：**模型调用**。因为后续所有能力——工作流、工具调用、检索增强、多智能体协作——最终都建立在这一层之上。

本章重点解决五个问题：如何定义角色与任务、如何组织上下文、如何约束输出、如何让模型结果被程序稳定接住、如何把一次调用封装成可复用模块。

---

## 1.1 起点：为什么要从模型调用开始

初学者容易把注意力放在更显眼的部分：工具调用、任务编排、多轮执行、自动检索、多智能体分工。这些能力当然重要，但它们不是起点，而是建立在模型调用之上的扩展。

如果模型输入设计不清晰、输出结果不稳定、返回格式不可控，那么后续叠加的每一层能力，都会**放大**这种不确定性：工作流会放大错误，工具链会扩散偏差，自动化执行会把局部问题带进整个系统。

这是智能体开发和普通"用一下模型"的区别。前者关心的不是模型能不能偶尔给出一个不错的回答，而是它能否在系统里**稳定工作**。

从工程角度看，这一步至少包含三件事：
1. 明确模型调用的基本结构
2. 降低输出漂移
3. 让结果能够被程序解析与消费

只有把这三件事处理清楚，模型才算真正从"只会生成文本的通用模型"，变成"可以进入系统的软件模块"。

> 模型调用不是智能体开发之前的准备动作，而是智能体开发本身的起点。

---

## 1.2 调用：一次受约束的对话

调用模型的本质，不是把一句话交给 AI，而是在**设计一次受约束的对话**。模型输出质量的上限，往往取决于你如何组织这次调用，而不仅仅取决于模型本身有多强。

### 1.2.1 从"问答"到"受约束的对话"

如果只是把模型当作聊天对象，一次调用可以很随意（"帮我分析一下这个需求"）。这类方式适合低风险、探索式场景。但智能体系统不接受"差不多就行"——一旦模型输出要进入工具调用、任务编排、状态更新或后续代码处理，开发者关注的就不只是"能不能答出来"，而是：

- 输入是否表达清楚
- 模型是否理解角色
- 上下文是否足够
- 输出格式是否可控
- 结果能否交给后续代码处理
- 相似输入下是否会严重漂移

当模型进入软件系统，它就不再只是一个对话界面，而是一个需要被设计、约束和验证的**系统组件**。

### 1.2.2 模型调用的最小结构：输入、约束与输出

一次完整的大模型调用，通常至少包含：**角色**（模型应以什么身份工作）、**任务**（这次要完成什么）、**上下文**（完成任务需要知道什么）、**输出约束**（结果应该以什么形式返回）、**后处理**（结果如何被解析、校验和继续使用）。

先定义"它是谁"，再说明"它要做什么"，接着补齐"它需要知道什么"，最后明确"它应该怎样输出"。

工程语境下，输入不是"最后一句用户提问"，而是一整个被组织过的上下文集合，可能包括：system 提示词、user 当前任务、历史消息、业务背景、代码片段、接口文档、模型参数、工具定义、输出格式要求。

输出也不只是"模型回答了什么"，它至少包含三层含义：
- **内容层**：文本是否围绕任务，逻辑是否清楚
- **结构层**：是否按要求返回，如 JSON、字段列表、代码等
- **消费层**：结果能否被程序解析、传递或触发下一步流程

> 在智能体开发中，输出的价值不在于表达是否流畅，而在于下游程序能否稳定解析、校验并继续处理。

### 1.2.3 system / user / assistant 分别承担什么

- **system**：系统级指令，用来定义长期稳定的角色、规则、边界和输出习惯。这里的 system 不是操作系统，而是模型调用中的最高层指令。
- **user**：用户级输入，用来描述当前任务、业务材料和本次要解决的问题。
- **assistant**：模型历史回复，用来维持多轮对话中的上下文连续性。

很多初学者习惯把所有内容都写进 user：角色设定、任务要求、格式约束、背景补充全部揉在一起。短期看似能工作，但任务一复杂，Prompt 越写越长，职责边界越来越模糊，模型行为也随之不稳定。

system prompt 的价值，在于提供一层相对稳定的全局控制：定义身份、设定边界（哪些事能做/不能做，信息不足时是否允许猜测）、统一风格、减少漂移（当 user 任务变化时，system 仍保持稳定约束）。

> user 解决的是"这一次要做什么"，system 解决的是"以后每一次都应该怎么做"。

### 1.2.4 一次完整调用的基本结构

从工程角度看，一次适合接入系统的模型调用，可以拆成五层：

| 层级 | 作用 |
|---|---|
| system | 定义全局角色、规则、行为边界和输出风格 |
| task | 描述本次调用要完成的目标 |
| context | 补充业务背景、代码片段、文档内容等必要信息 |
| format | 约束输出结构，如 JSON、字段、代码格式 |
| post-process | 对结果进行解析、校验、兜底、重试、记录 |

五层缺一不可：少了 system，模型行为容易漂移；少了 task，目标会模糊；少了 context，结果容易失真；少了 format，输出难以消费；少了 post-process，系统缺少闭环。

### 1.2.5 从一次请求到一项系统能力

适合工程系统的模型调用，不一定是最复杂的调用，而是最稳定、最可维护、最可扩展的调用，具备几个特征：

1. **分层清晰** — 角色、任务、上下文、输出约束不应混在一段 Prompt 里
2. **结构化输出** — 当模型结果要进入工具调用、任务编排、状态更新时，自然语言远远不够
3. **上下文有选择** — 上下文不是越多越好，而是要给足关键内容，减少噪声
4. **结果可校验** — 模型不是数据库，也不是确定性函数，进入系统的结果必须经过解析、校验、兜底和必要重试
5. **能力可封装** — 不应让每个业务模块各自拼 Prompt、各自解析结果、各自处理异常，模型调用应逐步沉淀成统一能力层

## 1.3 Prompt：不是提问，而是控制

Prompt 可以理解为模型调用时的指令集合。更准确地说，它不是"更高级的提问方式"，而是一份**轻量级行为契约**：规定模型是谁、要做什么、需要知道什么、应该如何返回，以及在什么情况下必须停止猜测。

在传统软件开发中，我们用函数签名、参数约束、返回结构和异常处理来规定一项能力如何被调用；在大模型系统中，Prompt 承担了类似职责。

> Prompt 的本质不是聊天技巧，而是一种轻量级的软件接口设计。

### 1.3.1 角色设定：先定义模型"是谁"

模型本质上是通用生成器。如果不限定角色，它会自行推断回答方式，有时像老师，有时像顾问，有时像程序员。

例如需求："帮我分析这个需求：用户上传 Excel 后，系统自动解析数据并生成日报。"

不设定角色，模型可能只给出泛泛描述。加上角色设定后：

> "你是一名资深产品技术分析助手，请从系统设计角度拆解需求，输出核心模块、潜在风险和待确认问题。"

输出会明显收束为结构化的核心模块、潜在风险、待确认问题三部分。

> 角色设定的价值不是让模型"演得像"，而是让分析视角更稳定。

### 1.3.2 任务定义：明确这次要完成什么

角色解决"它是谁"，任务定义解决"这次要做什么"。模糊任务会带来开放输出，例如"帮我看下这个功能怎么做"——模型不知道你要产品拆解、技术方案、数据库设计，还是测试策略。

更好的写法：

```
请将下面这个需求拆解为 3 个后端模块，并说明每个模块的职责：
"用户上传 Excel 后，系统自动解析数据并生成日报。"
```

代码生成也是一样，要写清楚输入输出、边界处理规则（忽略哪些数据、返回什么类型）。

> 任务越明确，模型越容易稳定地给出你真正需要的结果。

### 1.3.3 上下文补充：提供模型原本不知道的信息

模型再强，也不可能天然知道你的项目背景。例如"请为日报生成模块设计一个 API"——如果没有上下文，模型只能基于通用经验生成接口。真实项目往往依赖更多信息：系统是 REST 还是 GraphQL、鉴权方式、同步还是异步、字段命名规范、返回结构。

> 上下文的价值不在于多，而在于关键。好的上下文不是堆材料，而是筛出真正影响判断的要点。

### 1.3.4 输出约束：让结果从"能看"变成"能接"

在工程场景中，模型输出往往不只是给人阅读，还要进入系统。仅仅表达清楚不够，还必须让下游程序能够解析字段、校验类型，并把结果继续传给工具、工作流或数据库。

```
请分析下面这个需求，并按 JSON 返回：
{
  "summary": "",
  "modules": [],
  "risks": [],
  "questions": []
}
需求：用户上传 Excel 后，系统自动解析数据并生成日报。
```

进一步可以明确："请只返回 JSON，不要输出额外解释。所有字段必须保留；没有内容时返回空数组，不要省略字段。"

> 没有输出约束的 Prompt 更接近自由对话；有了输出约束，才接近可被程序调用的接口。

### 1.3.5 边界限制：明确不要做什么

很多 Prompt 只写"要模型做什么"，却很少写"不要做什么"。大模型默认倾向于给出完整、流畅、看似合理的回答。如果没有边界限制，它可能在信息不足时继续猜测，在任务模糊时自由扩展。

常见边界：不要编造不存在的字段、不要补充未提供的业务规则、不要输出额外解释、信息不足时必须说明不确定、只在给定上下文内回答。

> 边界限制的作用不是让模型减少输出，而是让系统在信息不足时能够安全失败，避免把猜测结果当作事实继续传递。

### 1.3.6 示例：从聊天式 Prompt 到工程式 Prompt

**聊天式**：`帮我分析一下这个上传 Excel 生成日报的需求。`

**工程式**：
```
你是一名产品技术分析助手。

请分析以下需求，并输出结构化结果：
需求：用户上传 Excel 后，系统自动解析数据并生成日报。

要求：
1. 从系统设计角度拆解需求
2. 输出字段必须包含：summary / modules / risks / questions
3. 每个 modules 元素需包含 name 和 responsibility
4. 如果信息不足，请在 questions 中提出，而不要自行补充业务规则
5. 最终按 JSON 返回，不要输出额外解释
```

第二种写法不只是表达更清楚，而是在定义一次可被程序承接的接口调用。

## 1.4 漂移：模型为什么会不稳定

如果 Prompt 是控制杆，这一节讨论的是：控制不到位时，系统会如何失控。常见现象：同样的问题结果不一样；前几次按要求输出 JSON，下一次突然夹带解释；有时很谨慎，有时又过度发挥。

### 1.4.1 不稳定通常表现在哪些地方

- **结果不一致**：同样输入下，粒度、重点和表达方式变化很大
- **格式漂移**：要求输出 JSON，却夹带解释、漏字段或改字段名
- **内容跑题**：要求分析风险，却开始讲背景或方案
- **看似合理实则有误**：用自信语气补出不存在的规则、字段或结论
- **保守与过度发挥摇摆**：有时频繁说信息不足，有时又擅自补全

### 1.4.2 温度参数会影响波动

temperature（采样温度）是模型生成时的随机性控制参数：温度越高，输出越发散；温度越低，输出越保守一致。结构化分析、代码生成、参数提取等工程任务，更适合较低温度。

> 温度只能减少随机性，不能替代清晰 Prompt。任务本身模糊时，低温度只会让模型"更稳定地模糊"。

### 1.4.3 上下文不足时，模型只能靠猜

例如"请为日报模块设计一个接口"表面明确，实际缺少很多关键信息（系统风格、鉴权方式、同步/异步、字段命名、返回结构）。缺口越多，模型需要猜的越多；猜测越多，输出波动越大。

> 很多时候，模型不是乱答，而是在填补你没有给出的空白。

### 1.4.4 任务不清楚，输出天然开放

"帮我分析这个功能"——"分析"可以指需求拆分、风险判断、技术方案、测试策略。只要任务有多种合理解释，输出就很难稳定。减少漂移的第一步不是调参数，而是把任务说清楚。

### 1.4.5 输出约束不足，会导致格式漂移

只写"请按 JSON 返回"，模型可能仍在 JSON 前后加解释、漏掉字段、改字段名、把数组变成字符串、无内容时省略字段。更稳定的写法需要逐条列出字段要求（见 1.3.4）。

> 输出稳定性的本质之一，就是约束强度。

### 1.4.6 如何收敛不确定性

| 不稳定原因 | 对应优化方式 |
|---|---|
| 温度过高带来的随机性 | 用合适温度降低随机波动 |
| 上下文不足导致的猜测 | 用关键上下文减少猜测 |
| 任务定义不清造成的多义性 | 用清晰任务定义减少目标偏移 |
| 输出约束不足导致的格式漂移 | 用输出约束降低格式漂移 |
| 缺乏校验机制导致错误扩散 | 用校验和兜底机制控制错误传播 |

> 真正的工程能力，不是要求模型永远不犯错，而是把不确定性收束到系统可以接受的范围内。

## 1.5 结构：让输出真正进入系统

即使内容大体正确，只要输出形态不可解析、不稳定，系统依然接不住。聊天场景里自然语言通常足够；但智能体系统里，模型输出往往要进入下一个任务节点、工具调用参数、工作流状态、数据存储结构、代码执行流程、评测与日志系统。模型结果必须从"能读懂"进一步变成"能处理"。

### 1.5.1 为什么自然语言不适合直接接系统

自由输出的自然语言，人能看懂，但程序很难稳定处理：哪一段是模块？哪一段是风险？待确认问题有几个？风险是字符串还是数组？系统需要的不是"差不多能懂"，而是"边界明确，能稳定读取"。

### 1.5.2 结构化输出的本质：可消费

按 JSON 返回后，模型输出就不再只是一段文本，而是一个可传递的结果对象：

```json
{
  "summary": "用户上传 Excel 后，系统自动解析数据并生成日报",
  "modules": [
    {"name": "upload", "responsibility": "处理 Excel 上传与基础校验"},
    {"name": "parser", "responsibility": "解析 Excel 内容并提取有效数据"},
    {"name": "report", "responsibility": "根据解析结果生成日报"}
  ],
  "risks": ["文件格式不统一", "字段缺失导致解析失败", "大文件可能导致处理超时"],
  "questions": ["日报模板是否固定", "是否支持多种 Excel 格式"]
}
```

`summary` 可展示，`modules` 可进入架构拆分，`risks` 可交给风险评估，`questions` 可形成澄清清单。

### 1.5.3 为什么 JSON 最常见

JSON 层次关系清楚、对人类可读、对程序易解析，前后端、脚本、工作流、日志系统都容易处理。但要注意：要求"按 JSON 返回"不等于结果一定稳定，字段约束、异常处理和结果校验才是关键。

### 1.5.4 结构化输出不只有 JSON

- **JSON**：通用接口结果、工具参数、状态对象
- **XML**：适合需要标签层级或历史系统兼容的场景
- **YAML**：适合配置、部署脚本、流水线定义
- **CSV**：适合二维表、批量字段导出、简单报表
- **choice / route**：适合任务分类、流程路由、Agent handoff
- **固定格式代码 / SQL / DSL**：适合直接进入执行或编译流程

> 结构化输出的核心不是统一格式，而是让模型结果以最适合下游接收的形式返回。

### 1.5.5 字段约束决定结构是否稳定

只写"请按 JSON 返回"远远不够。没有字段约束，模型可能一次叫 `modules`、下一次叫 `components`；一次 `risks` 是数组、下一次是字符串。更工程化的写法应明确顶层必须包含哪些字段、每个字段的类型、没有内容时返回空数组而不是省略字段。

### 1.5.6 异常处理：让系统能安全失败

结构化输出还必须考虑失败情况：JSON 解析失败怎么办？字段缺失/类型错误怎么办？更稳妥的做法是提前定义失败时的结构：

```json
{ "summary": "", "modules": [], "risks": [], "questions": ["信息不足，无法完成完整分析"] }
```

> 异常处理的本质不是让模型永远正确，而是让系统能够识别错误、接住错误，并决定是否重试或人工介入。

### 1.5.7 小结

结构化输出的意义，不是让模型看起来更规整，而是让模型结果具备**进入系统的条件**。自然语言适合人类交流；系统需要的是边界清晰、字段稳定、可解析、可校验的结果。

## 1.6 封装：从一次调用到一个可复用模块

> 模型调用进入工程系统的标志，不是会调 SDK，而是能把一次调用收束成可维护、可复用、可扩展的模块。

### 1.6.1 从最小可运行版本开始

任何工程化封装都不应该过早抽象。先把最小链路跑通：

```typescript
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  baseURL: "https://api.amux.ai/v1"
});

async function main() {

  });

```

这段代码只适合验证想法，不适合长期维护——业务逻辑、Prompt、模型参数和输出处理都混在一起。

### 1.6.2 不要把 Prompt 写死在业务代码里

第一版常见写法把 Prompt 拼在函数内部，角色设定和任务描述揉在一起，后续加日志、重试、校验时只能继续堆代码。更合理的方式是拆分：

```
src/
  llm/
    client.ts
    prompts.ts
    schemas.ts
    validators.ts
  services/
    requirementAnalyzer.ts
```

### 1.6.3 先定义结果，而不是直接消费自由文本

真正让模型调用开始工程化的，不是先抽象客户端，而是**先定义返回结构**——规定这项能力对外承诺返回什么数据：

```typescript
// src/llm/schemas.ts
export interface ModuleItem {
  name: string;
  responsibility: string;
}

export interface RequirementAnalysis {
  summary: string;
  modules: ModuleItem[];
  risks: string[];
  questions: string[];
}
```

### 1.6.4 封装统一模型调用层

把"发请求、拿结果、解析 JSON"抽成统一调用层：

```typescript
// src/llm/client.ts
import OpenAI from "openai";

export class LLMClient {
  private client: OpenAI;
  private model: string;

  constructor(model = "gpt-5.2") {
    this.client = new OpenAI({
      apiKey: process.env.OPENAI_API_KEY,
      baseURL: "https://api.amux.ai/v1"
    });
    this.model = model;
  }

  async generateText(systemPrompt: string, userPrompt: string): Promise<string> {
    const response = await this.client.responses.create({
      model: this.model,
      input: [
        { role: "system", content: [{ type: "input_text", text: systemPrompt }] },
        { role: "user", content: [{ type: "input_text", text: userPrompt }] },
      ],
    });
    return response.output_text;
  }

  async generateJSON<T>(systemPrompt: string, userPrompt: string): Promise<T> {
    const text = await this.generateText(systemPrompt, userPrompt);
    try {
      return JSON.parse(text) as T;
    } catch {
      throw new Error(`模型输出不是合法 JSON: ${text}`);
    }
  }
}
```

这层抽象统一了客户端创建、模型选择、system/user 输入组织、文本结果获取、JSON 解析。模型调用不再散落在各处业务函数里，而是有了统一入口。

### 1.6.5 Prompt 也要像代码一样可维护

```typescript
// src/llm/prompts.ts
export const REQUIREMENT_ANALYSIS_SYSTEM_PROMPT = `
  你是一名需求分析助手。
  你必须严格按 JSON 返回。
  如果信息不足，不要猜测，而是在 questions 字段中提出。
  不要输出额外解释。
`.trim();

export function buildRequirementAnalysisPrompt(requirement: string): string {
  return `
    请分析以下需求，并输出结构化结果。

    需求：
    ${requirement}

    返回字段要求：
    1. summary: 需求摘要
    2. modules: 模块列表，每个元素包含 name 和 responsibility
    3. risks: 风险列表
    4. questions: 待确认问题列表
  `.trim();
}
```

这样后续调整 system 规则、补字段、收紧边界或做 Prompt 版本管理，都不会污染业务代码。

### 1.6.6 把业务能力收束成模块

```typescript
// src/services/requirementAnalyzer.ts
import { LLMClient } from "../llm/client";
import { REQUIREMENT_ANALYSIS_SYSTEM_PROMPT, buildRequirementAnalysisPrompt } from "../llm/prompts";
import type { RequirementAnalysis } from "../llm/schemas";

export class RequirementAnalyzer {
  private llm: LLMClient;

  constructor(model = "gpt-5.2") {
    this.llm = new LLMClient(model);
  }

  async analyze(requirement: string): Promise<RequirementAnalysis> {
    const userPrompt = buildRequirementAnalysisPrompt(requirement);
    return this.llm.generateJSON<RequirementAnalysis>(
      REQUIREMENT_ANALYSIS_SYSTEM_PROMPT,
      userPrompt,
    );
  }
}
```

使用方式变得干净，拿到的不再是自由文本，而是有结构约定的结果对象。

### 1.6.7 结果校验、兜底和重试不是附加项

真正进入项目后，差距不在于"能否完成一次调用"，而在于异常发生后系统能否保持稳定：

```typescript
// src/llm/validators.ts
import type { RequirementAnalysis } from "./schemas";

export function isRequirementAnalysis(data: unknown): data is RequirementAnalysis {
  if (typeof data !== "object" || data === null) return false;
  const obj = data as Record<string, unknown>;
  return (
    typeof obj.summary === "string" &&
    Array.isArray(obj.modules) &&
    Array.isArray(obj.risks) &&
    Array.isArray(obj.questions)
  );
}
```

```typescript
// src/llm/utils.ts
export async function withRetry<T>(fn: () => Promise<T>, retries = 2): Promise<T> {
  let lastError: unknown;
  for (let i = 0; i <= retries; i++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error;
      await new Promise((resolve) => setTimeout(resolve, 500));
    }
  }
  throw lastError;
}
```

接入业务模块后，调用方不是在请求模型临时生成一个结果，而是在维护一项**带有不确定性的系统能力**。

### 1.6.8 为后续扩展留接口

现在的 `LLMClient` 虽然只做文本和 JSON 调用，但可以自然扩展出：工具参数、会话状态、metadata 日志与追踪、统一超时/重试/埋点、不同任务使用不同模型的路由策略。

从 Demo 走向模块，通常需要做到：Prompt 不写死在业务代码里、有统一模型调用层、Prompt 可维护可版本化、输出可校验有兜底、为链式调用/工具调用/状态管理预留扩展点。

## 1.7 示例：从需求摘要到代码生成

用同一个需求串三级递进示例，观察约束如何一步步收窄输出空间。

**需求描述**：运营同学每天会上传一份 Excel 文件，系统需要自动解析其中的数据，并生成一份日报。日报生成后支持导出，如果文件字段缺失或格式异常，需要给出明确提示。

### 1.7.1 从需求摘要开始（只加角色 + 输出框架）

```typescript
const response = await client.responses.create({
  model: "gpt-5.2",
  input: [
    {
      role: "system",
      content: [{ type: "input_text", text: "你是一名产品技术分析助手，擅长将业务需求拆解为功能目标、核心模块和潜在风险。请使用简洁、清晰的中文输出。" }],
    },
    {
      role: "user",
      content: [{ type: "input_text", text: `
请分析下面这个需求，并按以下三部分输出：
1. 功能目标
2. 核心模块
3. 风险点

需求：
运营同学每天会上传一份 Excel 文件，系统需要自动解析其中的数据，并生成一份日报。日报生成后支持导出，如果文件字段缺失或格式异常，需要给出明确提示。
      `.trim() }],
    },
  ],
});
```

模型被限定在明确框架里，输出更集中、更可预期。

### 1.7.2 从自然语言走向结构化结果

同一个需求，改成 JSON 输出，字段包括 `summary` / `modules` / `risks` / `priority` / `questions`，并配合运行时校验函数（同 1.6.7 思路）确认字段类型正确。从这一刻开始，模型输出不只是"看起来像对"，而要满足"结构上可被程序接受"。

### 1.7.3 代码生成场景

需求："写一个 Python 函数，接收一个用户列表，返回年龄大于 18 岁用户的邮箱地址，并处理空值情况。"

模糊写法只给一句话，模型容易默认字段都存在、忽略空值处理、返回值类型模糊。更工程化的写法需要明确：

```
请编写一个 Python 函数，要求如下：
1. 输入是一个用户列表，每个用户是一个字典，可能包含 name、age、email 字段
2. 返回年龄大于 18 岁用户的邮箱地址列表
3. 如果 age 为空、email 缺失或为 None，则跳过
4. 使用类型注解
5. 先简要解释思路，再输出代码
```

角色设定、任务定义、边界约束和输出要求，最终都会直接影响生成代码的质量。

> Prompt 的作用不是"让模型更听话"，而是在定义一份清晰的行为契约。

## 1.8 小结：如何让一次调用成为一项能力

工具调用、工作流编排、RAG、多智能体协作都很重要，但它们的前提不是掌握多少框架，而是先把一次模型调用设计成一个可控接口：

- 角色与任务边界清晰
- 上下文可管理
- 输出有明确契约
- 结果可解析、可校验
- 失败时能够安全兜底
- 调用逻辑可以封装复用

> 用 system/task/context/format 的分层收束不确定性，用结构化输出把"人能读懂"推进到"系统可处理"，再用 post-process 把模型结果纳入工程闭环。只有当这一层稳定下来，后续更复杂的能力叠加才不会放大混乱，而会沉淀为可维护、可复用、可扩展的系统能力。
