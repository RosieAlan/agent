# 第一章面试题 & 答案

### Q1：为什么说"调用大模型"和"跟 AI 聊天"是两回事？
聊天场景只要求"看起来合理"；工程调用要求结果能被系统稳定消费——包括格式可控、结果可复用、可测试、可校验。开发智能体关心的不是模型偶尔给出一个好答案，而是它能否在系统里稳定工作。

### Q2：system 和 user 的分工区别？
system 定义长期不变的角色、规则、输出习惯（"以后每次都该怎么做"）；user 描述当次具体任务和材料（"这一次要做什么"）。新手常犯的错是把两者都堆进 user，导致职责边界模糊、行为不稳定。

### Q3：一次适合接入系统的模型调用分哪五层？
system（角色/规则）、task（本次目标）、context（背景信息）、format（输出结构约束）、post-process（解析/校验/兜底/重试）。

### Q4：角色设定和任务定义的区别？
角色决定"以什么视角/身份看问题"（决定分析方向），任务定义决定"具体要产出什么、做到什么程度"（决定产出范围）。两者一个管视角，一个管范围。

### Q5：为什么边界限制（明确不要做什么）在智能体系统里特别重要？
没有边界限制时，模型在信息不足时不会说"不知道"，而是倾向于自信地编造一个看起来合理的答案。这在系统里很危险，因为下游容易把这种"格式规整、语气笃定"的编造内容当作事实直接使用。

### Q6：为什么上下文不是越多越好？
无关信息会变成噪声，掩盖真正重要的关键信息，模型需要自己去猜哪些是重点，猜错就会导致推理跑偏。关键信息 + 少噪声，比信息量大更重要。

### Q7：温度参数能不能替代清晰的 Prompt？
不能。温度只控制"输出的随机采样范围"，不改变任务本身是否清晰。如果任务定义模糊，调低温度只会让模型"稳定地给出同一个不准确的答案"，不会让它读懂你没说清楚的意图。

### Q8：为什么"要求返回 JSON"这句话本身还不够？
JSON 只是一种格式外壳，没有字段级约束时，模型仍可能改字段名、漏字段、把数组写成字符串。必须明确：顶层必须包含哪些字段、每个字段的类型、没有内容时如何处理（返回空数组而不是省略字段）。

### Q9：结构化输出的本质价值是什么？
不是"看起来整齐"，而是"可被下游代码消费"。自然语言给人看，边界清晰、字段稳定的结构才能被程序稳定提取、传递、触发下一步流程。

### Q10：为什么要先定义返回结构（schema），再写调用逻辑？
这是通用软件工程原则的迁移：先定义函数的返回类型，再写函数体的实现。先想清楚"这个能力该产出什么"，能避免写到一半才发现字段设计不合理，需要返工。

### Q11：为什么不能把 Prompt 写死在业务函数里？
写死会导致改 Prompt 就要动业务代码，两者耦合。拆开管理后：改 Prompt 不影响业务逻辑，能对 Prompt 做版本管理，也能统一给所有调用加日志/重试而不用满项目找散落的 Prompt。

### Q12：没有校验和重试机制会有什么后果？
没有校验：畸形数据（字段缺失/类型错误）会一路往下游传，可能在很远的环节之后才报错，排查成本极高。没有重试：模型调用偶尔的抽风（网络、格式问题）会导致整条链路直接失败，用户体验差；有重试通常能自动恢复，用户无感知。

### Q13（应用题）：设计一个"代码 review 意见"AI 功能，你会怎么设计这次调用？
- 角色：资深后端工程师，专注可读性/健壮性/安全性/性能
- 任务：审查这段 diff，指出问题给建议，不做无关风格争论
- 上下文：语言/框架版本、团队代码规范、这段代码的业务背景
- 输出格式：JSON，如 `{ issues: [{severity, line, description, suggestion}] }`，方便接入 CI 自动生成评论
- 边界限制：没把握的不要瞎猜；不建议改动与本次 diff 无关的代码；纯风格问题标记为 low，不与逻辑 bug 混淆

### Q14：这一章讲的所有东西最终服务于什么目标？
"打地基"——后续的工具调用、工作流编排、RAG、多智能体协作都建立在"能否设计好一次稳定调用"之上。这一层不稳，后面每叠加一层复杂度，错误只会被放大而不是抵消。
