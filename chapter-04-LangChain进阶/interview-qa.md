# 第四章面试题 & 答案

## 一、会话记忆 Memory

### Q1：大模型接口本身有记忆吗？ChatGPT 网页版为什么能"记住"前面的话？
没有。模型接口每次调用都是独立的，回答完就忘。网页版能"记住"，是因为客户端每次请求都把之前的聊天记录一起发过去，模型每次都重新读一遍全部记录再回答最新问题。

### Q2：多轮对话如果每轮只发当前输入，会出什么问题？
信息分散在多轮里，每轮单独处理时模型拿不到前文：第二轮只说"需求单号是 REQ-2026-001"，模型不知道是什么需求；最后要求"判断需求是否完整"时，模型只能反问要资料。接口每次都成功返回，但业务上已经失真。

### Q3：为什么需要 sessionId？
按会话隔离历史。多个用户同时对话，每个会话有独立的记录本，张三的历史不会被塞进李四的请求里。

### Q4：RunnableWithMessageHistory 每次调用做了什么？
① 用 configurable 里的 sessionId 取到该会话的历史记录；② 把历史放进 history 字段交给链；③ 执行链；④ 把本轮用户输入和 AI 回复自动存回历史。开发者不用手动取、拼、存。

### Q5：MessagesPlaceholder 和普通模板变量有什么区别？
普通变量 `{input}` 填入的是一段文字；MessagesPlaceholder 填入的是一整串消息（Human/AI 交替），用来把历史对话展开到 system 和当前问题之间。

### Q6：为什么要裁剪历史？
历史越长，每次调用越贵（按 token 计费）、越慢，还可能超过模型上下文上限。裁剪只保留最近、最有用的部分；裁剪只影响发给模型的内容，存储的完整历史不变。

### Q7（实战）：课程的 trimMessages 配置为什么导致多轮对话失忆？怎么修？
课程用 `tokenCounter: model`，按 OpenAI 分词方式计数，中文约 2.4 token/字，严重高估；而 `strategy: 'last'` 从最新一条往前保留，**最新一条自己就超预算时一条都不留**。模型回复较长时，第 4 轮历史被整体清空，模型失忆。修法：按条数裁剪，`tokenCounter: (msgs) => msgs.length` + `maxTokens: 10`（最近 5 轮）+ `startOn: 'human'`，不依赖分词器，也不会清空。

### Q8：`startOn: 'human'` 有什么用？
保证裁剪后的历史从用户消息开始，不会以一条孤立的 AI 回复开头，否则模型不知道那条回复在回答什么。

### Q9：最终报告为什么用 appendMessage 写回历史，而不是把问题重新交给 chat 跑一遍？
重跑要多调一次模型，花钱又慢；而且模型每次回答不同，重跑结果和用户实际收到的报告对不上。appendMessage 直接把"用户问题 + 最终报告"原样写入，不调模型，历史里记下的就是用户看到的内容。

### Q10：InMemoryChatMessageHistory 能用于生产吗？
不能，数据存在进程内存，重启即丢失，也无法多实例共享。生产应换 Redis 或数据库，接口不变（课程第五章换成数据库 messages 表）。

## 二、业务工具与安全

### Q11：为什么模型需要业务工具，而不是在 Prompt 里告诉它业务信息？
模型不知道需求单内容、公司规范这些真实数据，只能靠猜；把所有数据塞进 Prompt 既不现实也不及时。通过受控工具按需读取真实数据，模型负责决策，工具提供确定性结果。

### Q12：什么是路径穿越？工具的路径沙箱怎么做？
模型传入的路径来自用户输入，`../` 能跳出允许目录，例如 `../.env` 读到 API Key。沙箱做法：用 `path.resolve` 把相对路径算成真实路径，再检查是否仍在工作目录内。

### Q13（实战）：`resolved.startsWith(WORKSPACE_ROOT)` 有什么漏洞？
只比较字符串开头，名字开头相同的隔壁目录（如 `workspace-evil`）能绕过检查。修法：要求 `resolved === ROOT || resolved.startsWith(ROOT + path.sep)`。

### Q14：沙箱为什么必须写在工具代码里，不能靠 System Prompt？
Prompt 只是建议，用户换个说法、模型一糊涂就会照做；代码检查对任何输入都强制执行。

### Q15：工具执行报错时该怎么处理？
捕获异常，把错误信息作为工具结果（ToolMessage）交给模型，让它向用户解释，而不是让整个接口 500。工具出错也是一种结果。

### Q16：工具循环为什么要设上限？
防止模型反复调用工具停不下来，每一轮都要调模型、花钱，上限是保险丝。

### Q17：为什么需要多轮工具循环？
有些任务要先后调多个工具，且后一步依赖前一步结果（先查需求单 → 再读规范 → 再写报告），模型在第一轮无法一次安排好所有调用。循环直到模型不再申请工具为止。

### Q18：write_file 这类通用写入工具在生产中有什么问题？
让模型决定写哪个文件风险很大。生产中应收窄到明确业务目录、记录审计日志，更推荐通过业务服务写数据库记录，而不是把通用文件写入能力暴露给模型。

## 三、向量化与向量库

### Q19：什么是 Embedding？为什么能按意思搜索？
把文字转成一串数字（向量）的过程。模型经过训练，意思越接近的文字，向量越接近。搜索时把问题也转成向量，找最接近的几条。实测："怎样判断一个需求是否完整"与"核心功能、目标用户、业务目标三者齐全才算需求完整"相似度 0.68，与"会话之间互相隔离"只有 0.23，尽管没有共同关键词。

### Q20：向量搜索和关键词搜索的区别？
关键词搜索按字面匹配，换个说法就搜不到；向量搜索按语义匹配，能召回表述不同但意思相近的内容。

### Q21：embedDocuments 和 embedQuery 分别用在哪？
embedDocuments 在存资料时批量编码；embedQuery 在搜索时对单个问题编码。

### Q22：pooling 和 normalize 在做什么？
模型为每个分词各输出一个向量，mean pooling 取平均得到代表整句的一个向量；normalize 把向量长度缩放为 1，使余弦相似度等于点积，范围 -1 到 1。

### Q23：为什么自定义嵌入类要继承 LangChain 的 Embeddings？
遵循标准接口，向量库只依赖这个接口，不关心底层实现。以后换 OpenAI 嵌入只替换这一个类，上层代码不变。

### Q24：本地小模型和 API 嵌入模型怎么选？
本地模型（如 384 维 MiniLM）离线、免费、无密钥，但精度较低；API 模型（1536/3072 维）精度高但付费、依赖网络。小规模或教学用本地，生产按精度要求和成本权衡。

### Q25（实战）：国内环境下载 Hugging Face 模型失败怎么办？
表现为下载大文件中途卡住，报 `UND_ERR_BODY_TIMEOUT`。解法：用 curl 断点续传手动下载模型文件到本地，代码中设置本地模型路径并禁止联网下载，只读本地；镜像站也可能不稳定，要实测。

### Q26：MemoryVectorStore 的局限？
数据在内存中，重启即丢失，也不能多实例共享，只适合演示。生产用 PostgreSQL + pgvector 等持久化向量库。

## 四、多 Agent 编排

### Q27：为什么要把任务拆给多个 Agent？
一个大 Prompt 塞太多职责，模型容易顾此失彼、漏项；出问题难以定位是哪个环节；也无法在中途根据情况提前结束。拆开后每个 Agent 职责单一、提示词独立，可单独调优、换模型、加工具，也便于扩展新角色。

### Q28：什么时候不该用多 Agent？
一个 Prompt 配合少量工具就能稳定完成的任务不需要拆，多 Agent 带来更多调用次数、更高成本和更长延迟。

### Q29：固定编排里"澄清短路"有什么好处？
信息不足时在第二步就返回澄清问题并结束流程：避免硬编一份没有依据的报告；省掉后面三次模型调用的时间和费用；给用户可操作的下一步。

### Q30：为什么分析和风控能并行，汇总不能？
分析和风控只依赖抽取结果，互不依赖，可以用 Promise.all 同时执行，总耗时取较慢者；汇总需要它们两者的结果，必须等它们完成。

### Q31：抽取、澄清输出 JSON，分析、风控、汇总输出 Markdown，为什么？
抽取和澄清的结果要给代码读取做分支判断，必须结构化；后三者的结果是给人看的报告内容。

### Q32：编排里 JSON 解析失败怎么处理？
做宽松解析（去掉 Markdown 代码块包裹）；澄清结果解析失败时按"无需澄清"继续，不阻塞主流程；更稳的做法是对需要结构化的 Agent 使用结构化输出。

### Q33：常见的多 Agent 编排模式有哪些？
- Fixed Workflow：步骤写死，适合流程稳定的任务
- Router：先分类再分给专项 Agent
- Supervisor：主 Agent 根据每步结果动态决定下一步调谁
- Handoff：做完后把控制权和上下文交给下一个 Agent
- Planner-Executor：先规划任务清单再逐个执行，异常时重新规划

## 五、统一入口

### Q34：统一的 analyze() 入口做了什么？
调用编排做多 Agent 分析；需要澄清时直接返回问题；失败时返回转人工；成功时把报告写入文件，并用 appendMessage 把"用户输入 + 报告"写回会话记忆。

### Q35（实战）：课程的 analyze() 有什么不足？
编排只接收本轮输入，并没有读取会话历史，前几轮补充的需求单号、目标用户不会进入分析，记忆只是"写回"而没有"读取"；失败时会把"分析失败"文案当报告写入文件和历史；sessionId 直接拼进文件名，若包含 `../` 靠 safePath 拦截但会报错，入口处应校验 sessionId 格式。
