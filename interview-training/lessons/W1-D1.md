对应岗位：S1/S2/S3/S6/S7 的接口、全栈交付、模型接入与排错要求。当前为重学第一课和基线盘点。

对应原课程：第二章工程底座的请求/服务链路；第五章会话持久化中的 conversations/messages 用作存储案例。本课先建立完整流程，后续再学习对应章节的框架和数据库细节。

## 2026-10-15 首次短课与诊断补讲

用户本次约有一小时。安排：10 分钟反馈、20 分钟讲解、20 分钟浏览器取证、10 分钟复述批改。新增实操全部为只读观察或正常页面操作，现有服务由用户自行控制。

初次回答已提到拆需求和 Prompt，需补完整工程链路。后端读取服务端 .env 中的模型密钥，然后在访问供应商接口时进行鉴权；配置文件存放位置与模型调用是否联网分别考虑。本项目使用外部模型 API，需要网络连接。

历史存储需区分：PostgreSQL 是数据库系统，llm_chat 是聊天业务库，conversations/messages 是库中的两张表，id/content 等是表的字段，JSON 是数据格式。第一课先掌握“一个库里可有多张表，每条消息是一行”。本地 schema 已核对，消息 content 为文本、metadata 为可选 JSON。

示意数据，c1/m1/m2 均为教学 ID：

```text
conversations
id  userId  title
c1  u1      导入咨询

messages
id  conversationId  role       content
m1  c1              USER       最多能导入多少行？
m2  c1              ASSISTANT  当前规则是最多一万行。
```

messages.conversationId 指向 conversations.id，后端据此查出属于该会话的消息。用户归属由会话的 userId 校验。刷新页面时从数据库查询消息；继续对话时由后端把需要的历史放入本次模型输入。

浏览器取证作业：在 http://localhost:3002 打开 F12 → Network，选 Fetch/XHR，进入已有会话并点击“刷新历史”。找到 conversations/.../messages 请求，记录方法、路径、状态码、响应中的 role/content/conversationId，并核对两条消息的 conversationId。列表为空时先正常发送一条需求，再刷新历史；分析失败时可以先观察会话列表请求。提交前隐藏 Cookie、Authorization、令牌和私人正文。登录失效时通过页面重新登录。

页面可能请求 /api/workbench/conversations/.../messages，这是同源代理路径；后端业务路径为 /api/conversations/.../messages。观察本次实际请求确定 URL。此操作读取已保存记录，模型调用在发送新需求时才触发。

本次三道复测及标准答案：

1. 页面刷新历史时，谁访问数据库？后端验证用户和会话归属后查询数据库，再将消息返回页面。
2. c1 已有两条消息，再发一轮并成功得到回答，消息行数如何变化？按本项目每轮保存一条 USER 和一条 ASSISTANT 的方式，新增两行，共四行，conversationId 都是 c1。
3. .env 中存了模型密钥，程序怎样使用？后端读取配置，在请求供应商模型 API 时携带相应鉴权信息。浏览器调用本项目业务接口，由后端控制模型访问。

评分每题 10 分，按角色和因果准确 4 分、步骤或数据完整 4 分、能对应本次示例 2 分；三题至少 24 分且各题至少 6 分视为本小块通过。Cookie/完整令牌暴露先脱敏再提交，掌握情况依据独立作答登记。

## 目标

正式续课第一块（2026-10-15）：区分前端、后端、模型服务、数据库的职责。用“发送 Excel 导入需求”与“刷新历史”比较模型调用路径和持久化读取路径。三道理解检查：谁查询历史；后端怎样使用 .env 密钥；模型怎样拿到历史。标准答案分别为：后端校验后查询；读取服务端配置并用于上游鉴权；后端将所需历史加入本次模型输入。

本块实操：浏览器 Network 观察一次刷新历史，提交实际方法、路径和状态码。排错题：历史接口返回 401 且页面提示登录过期，先记录请求路径和脱敏响应，通过页面重新登录后复测同一请求。当前历史请求通常为 GET /api/workbench/conversations/<实际会话ID>/messages。服务由用户控制，理解检查与实操分别待验收。

## 从一条消息开始

用户在网页输入“解释一下 Excel 导入失败的原因”，点击发送。页面读取输入，将 JSON 请求发给后端；后端校验用户、读取本用户会话与必要资料，把消息提交给模型服务；模型返回文本，后端保存本次输入和回答，再返回页面显示。流式场景中，回答会分段传回，最终内容另按业务策略保存。

```text
浏览器页面 ── 用户输入 ──→ 后端接口 ── messages ──→ 模型服务
                             ↕                     │
                           数据库                   │
浏览器页面 ←── 回答/进度 ── 后端接口 ←── 模型结果 ────┘
```

前端负责输入、发送、加载/异常状态和显示。后端负责身份、权限、业务流程、模型凭据和持久化。模型服务根据收到的上下文生成输出。数据库负责保存业务数据和消息，后端按用户权限读取。

需求直接提出五个实现职责：接收输入、请求接口、验证身份/参数、调用模型、保存与返回。后续才把职责分配到页面、Controller、Service、模型适配器和数据库层。由任务职责推导文件，可以解释每个文件为什么存在。

本地参考项目的 3002 提供页面和同源代理，4002 处理身份，4001 处理业务分析。用户在浏览器统一使用 3002；内部服务按职责在不同端口监听。端口表示某个主机上的网络服务入口，同一项目可以包含多个服务。

## 密钥与历史

模型 API Key 属于服务端配置，浏览器向后端发送自己的业务请求。后端访问模型时携带模型凭据，日志与作业隐藏密钥和完整登录令牌。用户历史写入数据库后，下一轮由后端查询并选择必要内容传给模型。

模型当前能使用的信息来自本次调用及供应商明确提供的会话机制；本项目通过业务数据库加载历史，服务端组织本次上下文。数据库中保存了历史，只能说明数据可读取；模型是否收到历史还要检查实际请求构造。

## 必背标准答案

1. 前端负责收集输入和展示结果，后端负责身份校验、业务处理、调用模型和数据保存，模型服务负责根据收到的上下文生成输出，数据库负责保存消息和业务数据。
2. 一次 AI 请求经过页面发送、后端校验、加载必要上下文、调用模型、保存结果和返回展示。模型密钥放在服务端配置，消息按用户和会话保存并在需要时加载。

## 面试题与参考答案

### 第二块：HTTP 请求与响应（2026-10-15）

目标：必背请求由方法、URL、请求头和可选请求体组成，响应包含状态码、响应头与可选响应体；会用路径参数定位资源、查询参数补充筛选条件、JSON Body 提交内容；了解 HTTP 状态与业务状态是不同维度。

本地真实发送示例：POST http://localhost:3002/api/workbench/conversations/c1/chat/stream，请求头 Content-Type: application/json，请求体 {"input":"企业管理员需要批量导入 Excel"}。c1 为教学 ID，操作时通过页面使用真实会话。前端代码使用 fetch、method: 'POST'、JSON.stringify({ input: text })。流式响应的 SSE 事件和解析后续单独学习。

读取历史示例：GET /api/workbench/conversations/c1/messages。路径中的 c1 定位会话；?limit=20 是查询参数的教学示例，是否支持以对应接口实现为准。POST 用于本例提交分析，GET 用于本例读取历史，权限仍由后端校验。

JSON.stringify 将 JS 对象序列化为 JSON 文本；Content-Type 告诉接收端该请求体按 JSON 处理。后端仍需解析并验证字段。输入字符串空白、缺失或类型错误应按接口规则处理。

状态解释：200 表示该 HTTP 请求成功处理，具体业务完成情况还要检查 status 等约定字段；400 通常是请求输入错误；401 通常是身份凭据缺失或无效；403 通常是已识别身份但权限不足；404 可能是资源或路由未找到；500 是服务端内部错误。准确原因结合响应正文及服务端日志。SSE 连接建立成功后，也可能在事件中报告后续业务失败。

作业：① 拆解上述 POST 的方法、路径会话 ID、请求体和请求头；② Network 读取历史记录方法、路径、状态码，浏览器过滤可选 All 或 Fetch/XHR；③ 按场景定位：input 为空且返回 400、登录失效返回 401、访问他人会话返回 403。标准答案分别为核对字段与参数规则、登录凭据和身份校验、会话归属与访问权限。仅在自有测试账号及授权数据中实操，避免提交完整凭据。

理解检查及参考答案：① GET /conversations/c1/messages?limit=20 中，c1 为路径参数，limit 为查询参数；② POST 的新消息内容放本例 JSON Body 的 input；③ 200 与 status: need_clarification 可以同时成立，代表请求处理成功、业务等待补充。三题每题 10 分，沿用至少 24 分且各题至少 6 分的书面检查标准，实操另行登记。

### Q1：浏览器为什么把模型请求交给后端处理？

答案：后端集中保管模型凭据，并执行用户鉴权、数据权限、限流、费用控制和日志记录。页面通过业务接口使用能力。例如读取会话时，后端先验证它属于当前用户，再将允许的历史发给模型。

评分点：凭据位置、身份与数据边界、业务可控性。追问：页面改了 conversationId 后，哪一层阻止越权？答案：后端读取该资源时校验当前用户的访问权限。

### Q2：刷新后聊天记录还在，需要哪些条件？

答案：消息已经写入持久化存储；页面重新进入时取得登录身份和会话标识；后端验证归属并查询消息，页面重新展示。后续继续聊天时，后端还要选择历史内容加入模型上下文。

评分点：保存、查询、权限、模型上下文。追问：数据库有历史，模型仍然失忆，先检查哪里？答案：检查构造模型输入时是否实际加载并传入所需历史，以及裁剪是否丢失关键信息。

### Q3：模型调用返回 401，从哪里开始排查？

答案：先确认错误来自用户业务接口还是后端调用模型的上游；分别检查业务登录凭据，或供应商地址与凭据的配置和有效性。通过请求路径、状态码和脱敏日志取证，修复后复测同一个最小请求。

评分点：错误来源、对应凭据、证据与复测。追问：日志能记录什么？答案：请求标识、接口、耗时、状态码及脱敏错误；模型密钥和完整令牌需要隐藏。
