## 学完需要达到什么

- 必背：历史消息保存用户曾经说过什么；当前需求状态保存目前确认采用什么。用户明确修改同一需求的条件时，更新对应字段，保留其余有效信息，并记录修改依据。
- 会用：旧条件一万行、新条件五千行，能追踪输入、输出与证据；能解释“错误行导出”和管理员角色为什么继续保留。
- 了解：持久化状态、版本并发和人工确认会在W2/W3实现；本节只观察输入与模型结果，状态表用于设计说明。

## 一个具体变化

上一轮：“企业管理员需要批量导入Excel，最多一万行。”

这一轮：“改成最多五千行，错误行需要导出，其他要求保持不变。”

当前已知需求应保留管理员、Excel导入，行数上限改为五千行，增加错误行导出。原始一万行仍留在历史，方便解释变化过程。这个例子的更新规则来自同一用户对当前需求的明确修改；权限和系统规则仍由服务端约束。

| 内容 | 历史中的记录 | 当前采用的内容 | 依据 |
|---|---|---|---|
| 使用角色 | 企业管理员 | 企业管理员 | 第一轮，当前轮保留其余要求 |
| 功能 | 批量导入Excel | 批量导入Excel、错误行导出 | 第一轮加本轮补充 |
| 行数上限 | 一万行，随后改为五千行 | 五千行 | 本轮明确修改 |
| 行数口径 | 尚未说明 | 待确认 | 两轮均未说明单文件或累计 |

“增加错误行导出”属于补充；“改成五千行”属于修改；“五千行怎么样”是讨论方案，可能需要确认是否正式采用。识别变化之后仍要核对原文，避免把讨论自动变成已确认需求。

## 输入怎样进入模型

本轮输入顺序仍为system、上一轮user、上一轮assistant、本轮user。system规定任务边界；历史提供角色、文件和旧上限；本轮提供明确修改与新增功能。模型需要综合这些输入得到当前结论。

在现有文件中，最后一条user的content改成下面完整代码所示文本。模型工厂、历史和调用方式保持原有结构，便于对照变量。代码中的历史assistant仍为固定演示消息。

文件：`interview-training/labs/w1-d2/context-demo.ts`。

```ts
import '../../../chapter-02-工程底座/llm/services/chat/src/load-env.js';
import { createChatModel } from '../../../chapter-02-工程底座/llm/services/chat/src/llm/model.factory.js';

async function main() {
  const mode = process.argv[2] ?? 'history';
  const model = createChatModel();

  const history = [
    {
      role: 'user' as const,
      content: '企业管理员需要批量导入 Excel，最多一万行。',
    },
    {
      role: 'assistant' as const,
      content: '已记录需求，行数上限的适用范围待确认。',
    },
  ];

  const messages = [
    {
      role: 'system' as const,
      content: [
        '你是需求分析助手。综合本次提供的全部消息，',
        '输出需求摘要、已知约束、待确认事项。',
        '事实须有消息依据，缺失信息标为待确认。',
        '用户明确修改条件时，采用最新条件。',
      ].join(''),
    },
    ...(mode === 'history' ? history : []),
    {
      role: 'user' as const,
      content: '改成最多五千行，错误行需要导出，其他要求保持不变。',
    },
  ];

  console.log('实际发送的消息：', messages);
  const response = await model.invoke(messages);
  console.log('模型回复：', response.text);
}

main().catch((error: unknown) => {
  console.error(
    '调用失败，错误类型：',
    error instanceof Error ? error.name : '未知错误',
  );
  process.exitCode = 1;
});
```

## 从文字讨论走向可检查的业务状态

把每次采用的需求字段单独保存，可让前端、分析节点和导出功能读取同一个当前版本。对当前例子，状态至少需要角色、功能、行数上限、未确认问题，以及修改所依据的消息。状态字段由业务需要推导，后续再结合Schema验证和数据库设计实现。

本例“单文件还是累计”仍缺依据。可以先问：“五千行是每个Excel文件的上限吗？”字段与校验规则也需要确认。排期或正式执行需要哪些信息，由业务动作的前提决定；追问按阻塞程度排序，先处理会改变方案的重要条件。

## 必背答案与面试追问

1. 为什么同时保留历史和当前状态？历史支持追溯原始表达与修改过程；当前状态集中保存生效字段，供后续节点和页面使用。后端依据用户确认、权限与业务规则更新状态，记录来源，并确保下游读取正确版本。
2. 新旧条件冲突怎么处理？先判断是否为同一需求的同一字段，确认用户是否明确修改；明确修改则更新该字段并保留来源，其他字段继续沿用；表达模糊时先澄清。结构校验通过后继续核对语义与业务前提。

面试题A：“模型回复正确，排期仍按一万行计算，查哪里？”标准答案：查分析节点读的是历史旧结果还是当前状态，字段是否更新、更新是否落库、传给下游的版本是否一致。评分10分：读写链路4、状态/版本3、日志证据3。

面试题B：“用户说‘五千行怎么样’，可以立即把已确认上限写成五千吗？”标准答案：先识别为提议并询问确认，或由产品明确的交互规则解释其意图；保留当前确认值，记录候选值与未确认状态。评分10分：区分提议与明确修改4、状态与确认4、业务交互依据2。
