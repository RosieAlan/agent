## 本讲目标

必背：后端按会话保存历史，收到新消息后读取历史，将任务规则、历史和新消息按顺序放入本次模型请求。

会用：指出messages中system、user、assistant的来源，找出缺少的上一轮信息。

会排错：页面有历史而模型接不上时，检查本次实际请求的messages，再检查历史读取、会话选择与长度处理。

## 原课程的例子

第一轮：我们想做一个需求分析助手，希望它能记住多轮对话。
第二轮：需求单号是REQ-2026-001。

第一句提供需求内容，第二句补充编号。下面是阅读片段，沿用D01的model对象；assistant文字为示例，真实程序读取之前实际保存的回复。当前无需创建文件或请求模型。

```ts
const messages = [
  { role: 'system', content: '你是需求分析助手。根据本次提供的对话整理需求，缺失信息标为待确认。' },
  { role: 'user', content: '我们想做一个需求分析助手，希望它能记住多轮对话。' },
  { role: 'assistant', content: '已记录：需求分析助手需要支持多轮对话。' },
  { role: 'user', content: '需求单号是 REQ-2026-001。' },
];
const response = await model.invoke(messages);
```

messages是本次发给模型的消息数组。role记录角色，content记录文字。system由应用提供任务规则；user来自用户；assistant来自之前保存的模型回复。数组按对话顺序排列，最后一个对象是本轮刚收到的编号。

model.invoke(messages)把数组交给已经配置的模型；await等待回复；response接收返回的消息对象。需求内容与编号共同进入请求后，模型可以关联整理。若这次仅提供编号，这次输入就缺少原需求。

## 后端完整过程

收到本轮消息和会话编号 → 校验当前用户对该会话的访问权限 → 读取该会话历史 → 按顺序组装规则、历史与当前消息 → 调用模型 → 保存本轮用户消息与模型回复 → 返回前端。

页面显示旧消息、数据库保存旧消息，都需要后端继续读取并组装，旧消息才能进入本次模型请求。会话编号定位对话，可信登录身份用于权限校验。本轮消息在请求中出现一次，保存与读取顺序需要配合去重；事务和并发在后端单元展开。

## 三个词的具体含义

- 聊天历史：已经发生并保存的用户消息和模型回复。
- 本次上下文：这次真正发给模型的材料，包括规则、选入的历史和本轮消息，后续还可包括检索资料及工具结果。
- 会话记忆：程序管理历史，并让后续请求用到这些信息的能力。

## 必背标准答案

问：大模型应用怎样实现多轮对话？
答：后端按会话保存用户消息和模型回复。收到新消息后，读取当前会话历史，将任务规则、选中的历史和新消息按顺序组装成messages，再发给模型。长对话还需要控制长度并保留关键事实。

问：页面有历史，模型却接不上，怎么排查？
答：检查这次发给模型的messages里有没有需要的历史，再检查会话编号、历史读取、读取结果是否加入请求，以及长度处理是否删掉关键消息。日志查看角色和必要的脱敏内容，保护密钥和用户隐私。

## 阅读练习及答案

数据库保存了第一轮需求；第二轮调用仅发送system规则和“需求单号是REQ-2026-001”。问题在哪里，怎样修改？
答案：本次模型输入缺少第一轮需求。后端读取当前会话历史，把历史放在本轮用户消息之前，再调用模型。历史保存成功与模型输入完整分别检查。

独立口述：数据库已经存了历史，调用模型前还要完成哪两步？
标准答案：读取当前会话历史；把历史与本轮消息一起组装进messages。
