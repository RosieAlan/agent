# D04第三块：模型请求失败后，怎样有限重试

日期：2026-10-20。原课程第一章1.5.6异常处理、1.6.7结果校验/兜底/重试；第二章模型工厂统一组织配置。岗位对应：AI服务失败重试、并发限流、成本与超时控制。本块讲请求重试，入口限流和SSE在后续展开。

上一块学生页面显示“已取消本次请求”，前端取消显示通过；后端取消日志及取消后重提结果仍待验收。已有代码类型检查通过，相关证据继续复用。

## 目标与必背答案

必背：重试要先判断失败原因，对可能短暂恢复的请求失败设置有限次数和等待间隔；凭据、参数、额度等问题先修正原因。所有尝试共用本次请求的取消信号和总期限。maxRetries=2表示首次之外最多再试两次，总共最多三次。

会用：在模型工厂接收重试配置，为本课Service设置2；解释503、401、429额度不足及用户取消的处理。了解：退避、抖动、Retry-After、重复执行与幂等、多个重试层相乘、请求重试与结果修订各自的职责。

## 从一次真实处理过程理解

用户提交“员工报销超过2000元需主管审批”。第一次向供应商发请求，返回503，表示上游当前暂不可用；等待一段时间后第二次成功，页面最终得到结构化结果。若允许的三次都失败，错误继续交给上层处理。前端只提交了一次业务请求，后端在本次请求内部尝试了多次模型请求。

401通常要检查密钥；400检查请求参数；404检查地址和模型；额度不足检查额度/账单。它们需要对应修正。Schema校验失败要检查返回格式、Schema、Prompt与模型能力；原文2000变1000还要事实核对。这些问题都应保留具体原因，当前网络重试配置承担上游请求失败的有限重试。

## 原课程代码与本课选择

原1.6.7的withRetry用for循环、try/catch、500ms等待和最后抛错解释基本机制：i<=retries包括首次和额外重试。原示例捕获所有异常，且最后失败后还等待500ms，作为原理阅读保留。工程落地进一步按错误分类，使用当前安装适配器的有限重试，保留取消与总期限，避免再叠一层包住所有步骤的重试。

## 新词与API先解释

| 名称 | 本课含义 |
| --- | --- |
| maxRetries | ChatOpenAI构造配置的额外重试上限；0为只尝试首次，2为最多首次+两次 |
| 退避 | 连续失败后逐步增加等待，例如约1秒、2秒、4秒；实际间隔由实现决定 |
| 抖动 | 等待时间加随机变化，避免大量请求同一时刻再次冲上游 |
| Retry-After | 供应商响应头里的等待提示，可为秒数或HTTP日期；与总期限共同约束是否继续 |
| options | 本次给项目自定义createChatModel增加的普通配置对象参数，属于项目函数 |

maxRetries在创建模型对象时配置，在后续invoke遇到可重试错误时发挥作用。它控制尝试次数；每一次模型尝试仍会消耗延迟和可能的费用。当前项目OpenAI适配器内部SDK重试已设0，由LangChain caller负责当前这层请求重试，实测次数与配置一致。

## 本地版本实际行为：避免凭状态码猜测

安装@langchain/core 1.2.11、@langchain/openai 1.5.13。教师使用真实ChatOpenAI与本地固定HTTP响应验证：

| 模拟情况 | maxRetries | 实际HTTP次数 | 结论 |
| --- | --- | --- | --- |
| 503后成功 | 2 | 2 | 第二次成功后结束 |
| 持续503 | 2 | 3 | 达上限后抛错 |
| 持续503 | 0 | 1 | 仅首次尝试 |
| 401 | 2 | 1 | 直接抛出 |
| 404 | 2 | 1 | 直接抛出 |
| 429且insufficient_quota | 2 | 1 | 额度问题停止 |
| 429有短Retry-After提示，随后成功 | 2 | 2 | 等待并重试 |
| 429缺少等待提示 | 2 | 1 | 本地版本上交容量错误 |
| 取消正在等待的HTTP调用 | 2 | 1 | 结束当前等待 |

429包括频率限制、容量压力、额度耗尽等情况，结合error.code、响应头及供应商规范判断。当前版本对带短等待提示的429允许重试；等待提示过大、缺少提示时按容量问题交上层处理，额度不足停止。课堂代码沿用本地框架分类，不承诺任意兼容供应商的429都能自动恢复。

额外边界实测：第一次503之后的退避期间，50ms触发取消，底层未发第二次HTTP；invoke约1719ms后才返回错误。当前实现传入HTTP层的取消能阻止后续实际HTTP请求，退避计时本身的即时中断仍有边界。30秒是发出取消通知的期限，当前适配器在退避期间可能稍晚返回错误；严格响应期限需进一步实现可中断等待或由业务取消边界包住，作为D04综合排错项保留。页面手动取消的本地提示可以先出现。此限制明确登记，当前未标为即时释放全部资源。

## 学生修改：两处小改动

文件一：chapter-02-工程底座/llm/services/chat/src/llm/model.factory.ts。只改createChatModel函数签名，并在其new ChatCompletionsOpenAI配置里增加maxRetries；已有类、代理、模型配置和密钥读取保留。

完整createChatModel函数如下，可替换原文件的同名函数：

```ts
export function createChatModel(
  options: { maxRetries?: number } = {},
) {
  const config = loadLangChainConfig();
  const keys = getApiKeys();
  const proxyUrl = process.env.HTTPS_PROXY ?? process.env.HTTP_PROXY;

  return new ChatCompletionsOpenAI({
    model: config.llm.model,
    temperature: config.llm.temperature,
    maxTokens: config.llm.maxTokens,
    maxRetries: options.maxRetries,
    apiKey: keys.openaiApiKey,
    configuration: {
      ...(keys.openaiBaseUrl ? { baseURL: keys.openaiBaseUrl } : {}),
      ...(proxyUrl
        ? { fetchOptions: { dispatcher: new ProxyAgent(proxyUrl) } }
        : {}),
    },
  });
}
```

`options: {maxRetries?:number}`说明参数是对象，里面可提供数字maxRetries；`={}`允许原来无参数的createChatModel()继续使用。它们未指定重试数时沿用库的默认行为；本课Service明确指定2，避免把默认值当作自己已制定的策略。

文件二：chapter-02-工程底座/llm/services/chat/src/llm/requirement.service.ts。找到：

```ts
  private model = createChatModel();
```

替换为：

```ts
  private model = createChatModel({ maxRetries: 2 });
```

这行执行时先创建配置对象，项目工厂把2传给ChatOpenAI构造配置，后续模型调用按此上限执行。Controller和练习页保持当前取消实现。

## 总期限与重复执行

保持原Service在invoke外创建timeoutSignal，首次请求、等待退避、后续尝试共用该信号。若每次失败都新建30秒计时器，三次尝试会让单次业务请求等待明显延长。当前底层退避的中断返回延迟见上方已验证边界。

同时启用多个重试层时要核对总尝试数：外层最多3次、内层每次最多3次，最坏可能出现9次上游请求。当前结构只显式配置模型请求层；结构化解析错误不因该配置自动再次生成。需要修复格式时另设有次数边界的修订步骤，课程优化闭环中继续学。

纯文本分析重复请求主要增加成本与时延。创建订单、扣款、发消息等写操作涉及重复执行后果，要先设计幂等标识、查询结果与权限审批；工具治理单元继续详细实现。

## 面试题及完整答案

1. 怎样设计模型重试？先按请求错误分类，对短暂可恢复错误设置重试次数、退避和随机等待，参考Retry-After；共享取消与总期限，核对框架与SDK叠加，并记录次数和最终原因。凭据/参数/额度先修正原因，结果错误另做格式或事实处理。
2. maxRetries=2总共几次？首次加最多两次重试，共最多三次；首次成功立即结束。首次401时本地适配器直接抛错，模拟只有一次HTTP；用户取消后停止继续实际HTTP请求，当前退避返回延迟需按实现验证。
3. 429如何处理？结合错误码、等待提示、供应商规范和业务剩余期限分类；短时频率限制可等待重试，额度耗尽处理账单或配额，容量不足可提示稍后或按明确策略降级。本地实测缺少等待提示的429上交容量错误。
4. 重试和限流各解决什么？重试处理已经失败的请求；限流控制进入系统或供应商的请求量，减少过载。下一块实现入口限流与并发控制的区别。
