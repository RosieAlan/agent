# D02第四主题：控制本次输入，保留关键条件

日期：2026-10-19。原课程：第四章4.2.2；第十章预算作前置，完整成本实验在D24。独立裁剪实测按既有约定在D05综合检查。

## 目标与数据流

必背：完整记录与本次模型输入分别管理；按预算选消息；已确认关键条件单独保留并纳入预算。会用：解释trimMessages配置、计算历史额度、定位关键事实丢失。了解：摘要与检索也占预算，来源和有效版本需要核对。

此前checkpointer按thread_id保存状态，MemorySaver把状态放在进程内。会话继续累积后，每次调用模型都需要选择本次发送内容。完整记录用于回看和追溯，本次输入用于回答眼前问题。对读取出的数组做选择，可以保留原记录；修改图状态或数据库记录属于另一次写入。

案例：第一轮用户确认“需求助手的历史保存30天”，随后讨论几十轮按钮颜色，最新问题是“历史保存多久”。按最近顺序裁剪时，30天可能被排除，本轮模型输入因此缺少保存期限。

## Token与预算

Token是模型处理文本的计量单位，由分词规则决定。上下文窗口是单次处理容量，实际输入、输出上限需查所选模型与供应商规则。

计算例假设输入加输出总容量10000 Token，预留输出2000、安全余量500、系统要求与已确认条件1000、本轮问题500：历史额度=10000−2000−500−1000−500=6000。该容量仅为教学假设。实际还需计入工具定义、检索资料与消息包装开销，最终合并后重新计数。输入裁剪额度和模型回答最大长度分别配置。

历史持续增长，重复发送的输入通常随之增加，费用、延迟和干扰也可能增加。缓存计费与推理Token的完整成本实验在D24。

## trimMessages逐项解释

来源：@langchain/core/messages。用途：接收消息数组，按预算和顺序返回选中的消息。执行时机：取到候选内容后、调用模型前。返回值：Promise<BaseMessage[]>，await后得到数组。

下面为阅读片段，复用memory-current.ts已创建的agent、configA、model。它独立展示读取与选择，createAgent自动调用前的接入实作纳入D05综合检查。

```ts
import { trimMessages } from '@langchain/core/messages';

const snapshot = await agent.getState(configA);
const history = snapshot.values.messages;

const selected = await trimMessages(history, {
  maxTokens: 2000,
  strategy: 'last',
  tokenCounter: model,
  includeSystem: true,
  allowPartial: false,
  startOn: 'human',
});
```

| 配置或变量 | 作用 |
|---|---|
| history | 本次待选择的消息数组 |
| maxTokens | 返回数组的计数预算，这里为2000 |
| strategy: 'last' | 优先选择靠后的消息 |
| tokenCounter: model | 使用模型对象提供的消息Token计数能力，精度取决于适配器 |
| includeSystem: true | 输入首条为系统消息时，按规则保留；该消息也占预算 |
| allowPartial: false | 以完整消息为单位保留 |
| startOn: 'human' | 对话部分从用户消息开始，保留的系统消息可放在前面 |
| selected | 裁剪后的新数组，后续应使用它构建本次发送内容 |

createAgent的systemPrompt单独配置，getState中的messages可能仅含对话。系统要求仍需单独计入总预算。includeSystem只处理输入数组中实际存在的首条系统消息。

原文4.2.2用配置形式创建trimmer再invoke，本讲采用本地版本支持的直接调用形式。strategy:last按位置选取，语义相关性需要另外的筛选或检索逻辑。

## 关键条件保留与失败处理

完整历史保留原话与时间；当前已确认条件保留保存期限、适用角色和确认来源；本次输入组合系统要求、当前条件、近期消息与本轮问题。用户明确修改条件后，更新当前字段和版本，再计算本次输入预算。

摘要用于压缩讨论，需核对遗漏和事实。向量检索用于召回相关旧片段，召回内容仍占预算，权限、来源和有效版本都要检查；完整RAG在D13–D16。

- 旧关键条件丢失：查看实际发送内容，补入已确认字段或核对过的摘要，再计数。
- 长度仍超限：核对系统要求、工具定义、资料、本轮问题和输出预留。
- 本轮单条消息已超预算：预先检查，选择分段处理、压缩或提示缩短输入，并给出明确处理结果。
- 工具消息被拆散：D06结合工具调用ID、回复配对及供应商消息格式完整练习。

## 必背答案与检查题

面试：聊天历史越来越长，怎么处理？

答：完整记录保存在会话存储中，每次调用前按Token预算选择本次输入。我会预留输出和安全余量，计算系统要求、工具、资料及当前问题的占用，再给历史分配额度。近期消息按顺序裁剪，已确认关键条件单独维护，必要时加入核对过的摘要或相关旧片段，最终检查实际发送内容与总长度。

检查一：上例历史额度多少？答：6000 Token。

检查二：第一轮确认30天，近期仅讨论颜色，本轮模型回答保存期限未知，优先查什么？答：查看本次实际发送的messages与系统内容，确认30天是否被裁掉、当前已确认条件是否带入。时间较早的条件仍可能对当前回答十分重要。
