## 业务问题和数据流

第一轮用户：“企业管理员需要批量导入Excel，最多一万行。”

第二轮用户：“补充：错误行需要导出，其他要求保持不变。”

第二轮分析需要保留管理员、Excel导入、一万行，并增加错误行导出。只发送第二轮时，模型收到的信息只明确错误行导出和延续要求，其他内容缺少依据，合理行为是追问或标记待确认。

前端发送本轮输入与conversationId → 后端验证身份及会话归属 → 读取历史/业务状态 → 组织system、历史user/assistant、本轮user → invoke → 保存及返回结果。历史显示在页面、历史存进数据库、历史进入模型输入分别检查。

本节比较两种messages：只含system+当前user，共2条；包含system+固定历史user/assistant+当前user，共4条。重复使用同一个model调用客户端时，业务代码仍负责本轮messages。使用记忆封装或服务端会话机制时，上下文装配由对应机制承担；本节沿用直接invoke。

## 为什么只增加一个练习文件

已有createChatModel集中维护配置和兼容策略。新context-demo.ts只组织对照输入和调用，先看清消息传递，再接数据库历史。固定历史assistant消息是演示样本，真实业务从已有会话读取；明确业务事实以用户输入和可信业务资料为依据。

由学生创建`interview-training/labs/w1-d2/context-demo.ts`，目录不存在时先创建w1-d2。完整文件如下；复用已有模型工厂，依赖沿工厂所在项目解析，无需新增依赖。

```ts
import '../../../chapter-02-工程底座/llm/services/chat/src/load-env.js';
import { createChatModel } from '../../../chapter-02-工程底座/llm/services/chat/src/llm/model.factory.js';

async function main() {
  const mode = process.argv[2] ?? 'history';
  const model = createChatModel();

  const history = [
    {
      role: 'user' as const,
      content: '企业管理员需要批量导入 Excel，最多一万行。',
    },
    {
      role: 'assistant' as const,
      content: '已记录需求，行数上限的适用范围待确认。',
    },
  ];

  const messages = [
    {
      role: 'system' as const,
      content: [
        '你是需求分析助手。综合本次提供的全部消息，',
        '输出需求摘要、已知约束、待确认事项。',
        '事实须有消息依据，缺失信息标为待确认。',
        '用户明确修改条件时，采用最新条件。',
      ].join(''),
    },
    ...(mode === 'history' ? history : []),
    {
      role: 'user' as const,
      content: '补充：错误行需要导出，其他要求保持不变。',
    },
  ];

  console.log('实际发送的消息：', messages);
  const response = await model.invoke(messages);
  console.log('模型回复：', response.text);
}

main().catch((error: unknown) => {
  console.error(
    '调用失败，错误类型：',
    error instanceof Error ? error.name : '未知错误',
  );
  process.exitCode = 1;
});
```

## 代码与运行

history保存两条固定历史消息。messages保留任务规则，按mode决定是否加入history，最后追加当前user。数组展开让历史消息逐条进入同一个输入数组；每条消息保留其角色。console.log打印这次真正发送的内容，便于观察断点。此演示使用虚构需求，实际业务日志需要脱敏与范围控制。

真实调用需从services/chat加载.env及config/langchain.yaml。先在编辑器创建上述文件，再在PowerShell运行：

```powershell
cd 'C:\Users\Administrator\Desktop\newAgent\agent-course\chapter-02-工程底座\llm\services\chat'
bun run ../../../../interview-training/labs/w1-d2/context-demo.ts no-history
bun run ../../../../interview-training/labs/w1-d2/context-demo.ts history
```

每条命令发起一次真实模型请求，共两次，服务端进程和Docker均非该脚本前提；本地模型配置、密钥及供应商可用性仍需满足。

验收只传当前消息时打印2条，带历史打印4条。带历史应有依据地保留管理员、Excel、一万行并补充错误行导出；只传当前消息时应将缺失主体和约束列待确认。模型可能凭常识猜测，按实际发送消息判断有无依据，措辞不固定。两次调用使用同一系统Prompt和本轮输入，变化只有历史。

## 必背与面试题答案

必背1：messages组织本次模型可使用的任务规则、必要历史和当前输入；直接invoke的业务代码负责装配这些内容。必背2：历史存储负责保存，历史装配负责选择并加入模型输入，业务应用分别验证两步。

题1：页面有第一轮消息，模型仍追问“导入什么文件”，查哪里？答案：检查后端实际invoke的messages，确认是否加载正确会话历史、是否被裁剪、是否传入模型，继续核对查询结果与最终输入之间的装配。评分10分：实际输入4、历史加载/装配4、裁剪2。

题2：只把conversationId放进普通user文本，模型能自动查数据库吗？答案：会话编号是标识数据；后端需要按权限查询历史并加入消息，或提供受控工具执行检索。本节的直接ChatModel调用通过应用装配历史。评分10分：编号职责3、后端查询与装配4、权限3。

实操A：提交两种模式的消息条数和模型回复，说明哪条输入为“最多一万行”提供依据。独立修改B：将当前用户补充改为“改成最多五千行，错误行需要导出”，带历史时检查更新为五千行。口述C：历史已保存在数据库，为什么还需要构造messages？参考答案：数据库提供持久化数据，后端构造messages把相关历史变成本次模型输入。旧作业保持待收尾。
