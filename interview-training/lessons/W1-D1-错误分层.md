# W1-D1：模型调用失败，怎样定位出错阶段

日期：2026-10-16。对应原第三章3.7结构化输出及第一章调用异常；衔接第十六章日志、可观测性。岗位项：模型接入、后端异常处理、运行时校验。当前学习阶段为W1-D1最后一个小目标；W1-D4还会进一步实现超时、取消、重试与SSE。

## 学习目标与上一块答案

必背：请求阶段检查上游调用；JSON解析阶段检查文本语法；Schema阶段检查字段和类型。按失败阶段选择修复位置，成功数据继续做事实与业务检查。

会用：运行四个本地样本，通过stage、错误类型、状态码或字段路径定位失败；独立改变一个非法字段并预测结果。

了解：withStructuredOutput把生成、解析和校验封装在一次调用内，实际错误可能经过框架包装，需要结合调用堆栈、HTTP状态、cause和校验明细判断。

上一块标准答案：Prompt规定任务、字段语义和事实规则；Schema规定字段及数据约束。普通invoke返回模型消息，response.text取文本；传入Zod Schema的withStructuredOutput成功返回解析校验后的对象，业务代码可读result.features。结构符合要求和内容有原文依据分别验收。

## 一条需求经过哪几步

输入“企业管理员要导入Excel，最多一万行”后：后端向模型供应商请求 → 得到文本 → JSON.parse得到JS值 → Schema检查字段及类型 → 应用核对事实并决定是否追问。

本节把中间三个阶段显式写出，便于观察。对照真实structured-call.ts时，其invoke内部可能完成上述多个阶段。

| 阶段 | 故障例子 | 判断依据 | 修复方向 |
|---|---|---|---|
| request | 供应商返回429 | 本节stage=request、status=429 | 实际环境核对限流、配额和请求节奏 |
| parse | 返回半截`{"features": [` | stage=parse、SyntaxError | 检查输出是否截断、输出协议与原始文本 |
| validate | 返回`features: 123` | stage=validate、ZodError及features路径 | 检查字段约束、实际输出、结构化方式和模型兼容性 |

三类示例各有一个故意制造的故障。真实系统的请求、解析、校验也可能受网络、框架或代码错误影响，stage表示失败位置，详细证据进一步说明原因。

## 为什么新增这个文件

schema.ts继续定义已有三字段约束。新文件failure-demo.ts只负责提供固定样本、按顺序处理、输出诊断。固定样本让每次都能稳定复现同一个故障，也节省模型调用费用。

学生手动创建：`interview-training/labs/w1-d1/failure-demo.ts`。这是正式学习练习，后续保留。当前提交保存讲义，学生脚本在提交作业后检查与归档。

下面是完整文件内容，依赖已有schema.ts和本地Zod3.25.76；所有响应均由本地函数模拟，联网调用次数为0。

```ts
import { z } from 'zod';
import { RequirementSchema } from './schema.js';

const mode = process.argv[2] ?? 'success';

async function getDemoResponse(): Promise<string> {
  if (mode === 'upstream') {
    throw Object.assign(new Error('模拟上游限流'), {
      status: 429,
    });
  }

  if (mode === 'json') {
    return '{"features": [';
  }

  return JSON.stringify({
    features: mode === 'schema' ? 123 : ['导入 Excel'],
    constraints: ['最多一万行'],
    missingInformation: ['一万行的适用范围待确认'],
  });
}

async function main() {
  let stage: 'request' | 'parse' | 'validate' = 'request';

  try {
    const text = await getDemoResponse();

    stage = 'parse';
    const data: unknown = JSON.parse(text);

    stage = 'validate';
    const result = RequirementSchema.parse(data);

    console.log('成功：', result);
  } catch (error: unknown) {
    console.error('失败阶段：', stage);
    console.error(
      '错误类型：',
      error instanceof Error ? error.name : '未知错误',
    );

    if (error instanceof z.ZodError) {
      console.error('字段问题：', error.issues);
    }

    if (
      typeof error === 'object' &&
      error !== null &&
      'status' in error
    ) {
      console.error('状态码：', error.status);
    }

    process.exitCode = 1;
  }
}

void main();
```

## 逐段理解

mode读取命令行参数：success为合法样本，upstream模拟请求抛错，json给出半截文本，schema给出合法JSON但字段类型错误。代码仅定义这四个练习参数，其他参数也会走默认合法样本，验收使用指定值。

getDemoResponse模拟请求边界。throw使Promise拒绝，await把异常交给catch；其他分支返回字符串，供后续阶段处理。upstream案例的Error和429由练习代码构造，与真实供应商状态分别记录。

stage在每项操作之前更新。JSON解析抛错时stage停在parse，Schema校验抛错时停在validate；后续语句会跳过并进入catch。unknown要求代码先检查数据，再读取其字段。

JSON.parse负责把JSON文本变成JS值；RequirementSchema.parse负责运行时字段和类型校验。上一块用safeParse返回success结果，本块用parse在校验失败时抛出ZodError，便于统一观察catch。两者都执行Schema校验，差别是失败的交付方式。

error.issues提供错误字段路径、期望类型等明细。process.exitCode=1把本次运行标记为失败，终端和脚本可以据此判断；错误内容继续保留在日志中。真实应用还会输出稳定的业务错误码、traceId和安全的用户提示，后续工程化练习实现。

## 对照真实模型错误

此前上游404排查：确认实际模型ID及账号可用权限 → 脱敏baseURL和实际请求路径是否匹配 → 查看调用协议/适配器、状态码、响应及请求编号。当前项目曾涉及Responses和Chat Completions端点兼容，错误栈有助于判断实际请求路径。SDK给出的MODEL_NOT_FOUND标签需要与上游响应共同判断；404可能涉及端点路由或模型资源等多个原因。

withStructuredOutput出错时，记录安全的错误类型、状态码、堆栈/cause及字段明细。解析器可能把底层失败包装为OutputParserException或OUTPUT_PARSING_FAILURE等，因此实际分类以证据为准。本节手写链路用于看清边界，当前结构化脚本继续使用框架封装。

401/404先核对凭据、模型及端点；429/临时服务失败按供应商提示、Retry-After和错误含义决定是否退避重试，设置次数及总时长上限。实际策略需要统一SDK和业务层重试预算，后续课程落地。JSON/Schema失败检查输出和协议，修复后用故障样本回归。业务失败向后续流程传递明确状态。

## 必背答案、面试题与作业

必背1：请求失败表示调用阶段出了问题；JSON解析失败表示文本无法按JSON语法读取；Schema失败表示解析后的值与字段、类型或约束不匹配。排错先确定失败阶段，再查该阶段证据。

必背2：JSON.parse检查JSON语法并生成JS值，Schema检查数据结构与约束，事实校验检查内容是否有依据。三项检查分别负责各自边界。

面试题1：上游HTTP为200，结果features为123，失败可能发生在哪里？答案：HTTP成功表示请求层成功；数字123是合法JSON值，满足语法；本Schema要求features为数组，因此运行时校验在features路径失败。评分10分：HTTP边界3、JSON合法2、Schema字段证据5。追问：features改为['导入十万行']会怎样？答案：结构可通过，原文一万行与十万行需要事实校验识别。

面试题2：为什么catch里全部返回空数组会影响可靠性？答案：空数组本身可满足此Schema，调用方可能把失败误读为没有功能或没有缺失信息；应保留失败状态、错误码和诊断证据，应用按错误类型重试、提示或终止。评分10分：空数组语义3、状态传播4、分类型处理3。追问：真实供应商429怎么复现才节省费用？答案：用本地模拟异常先验证控制流，真实环境对照安全日志和限流策略。
